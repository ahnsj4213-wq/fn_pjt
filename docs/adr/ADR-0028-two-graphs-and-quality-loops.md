# ADR-0028 — LangGraph 두 개(면접 실행·평가)와 질문·평가 품질 검증 루프

- 상태: 채택 (2026-11-11, 사용자 지시)
- 관련: ADR-0016(면접 진행 그래프), ADR-0020(회사 자료 RAG), ADR-0022·0025(live/upfront 질문), ADR-0023·0026(평가·루브릭), ADR-0024(이탈 = 종료), ADR-0027(세 흐름 정리 — 이 ADR이 구조를 대체)
- 영향: API·DB 스키마 변경 없음. 프롬프트 버전 T2 `question_generate@1.9.0`, T3 `resume_question@1.7.0`, T5 `evaluate_answer@2.2.0`.

## 배경

ADR-0027은 그래프를 셋(질문 생성, 면접 진행, 평가)으로 두었다. 다음 문제가 있었다.

- **질문 생성과 면접의 연결이 숨어 있었다.** live 모드에서는 질문 생성과 면접이 실제로 한 흐름이다. 그런데 다음 질문 만들기가 면접 노드 안의 숨은 호출(`live.ensure_next`)이었다.
- **질문 재생성 경로가 셋이었다.** T2·T3 안의 재생성, RAG 2라운드, 컴포저의 개별 검사가 따로 있어 상한을 한눈에 볼 수 없었다.
- **평가 쪽 검사가 인용 대조뿐이었다.** 점수·이유·인용이 서로 맞는지, 표본 판정끼리 일관된지는 보지 않았다.

## 결정

### 1. Graph 1 — AI 면접 실행 (`app/interview/graph.py`)

```
START -> start -+-(COMPOSE)---> plan -> project -> motivation -> job_skill -> write -> END
                +-(INTERVIEW)-> compose_next -> present -> ask -> wait_answer(interrupt) -> transcribe
                |                    ^                                                       |
                |                    +------------------ decide_followup <-------------------+
                |               compose_next -> present | finish | END(텍스트 모드)
                |               finish -> END (코딩 있으면 CODING, 없으면 SUBMITTED + 평가 등록)
                +-(SUBMIT)----> coding_submit -> END (코딩 최종 제출: 스냅샷·채점·평가 등록)
                +-(할 일 없음)-> END
```

- **그래프는 하나, 체크포인트 thread는 입구마다 따로다(PR #2 리뷰 반영).**
  - 면접: `<지원서 id>`
  - 질문 구성: `compose:<지원서>:<설정 버전>`
  - 코딩 제출: `submit:<지원서>`
  - 각 입구는 자기 thread만 쓰고 지운다. 그래서 늦은 질문 구성 재시도나 중복 제출이 대기 중인 면접 체크포인트를 덮거나 지우지 못한다.
  - `purge_finished` 보관 기준: 질문 구성 thread는 응시가 READY·PREPARING일 때, 제출 thread는 CODING일 때 남긴다.
- **면접이 시작된 뒤 끝난 질문 구성은 아무것도 쓰지 않는다.** `start`는 응시 상태가 READY·PREPARING일 때만 구성을 시작한다. `write`는 지원서를 잠근 뒤 상태를 다시 확인한다. 상태가 바뀌었으면 쓰고 있는 세트를 SUPERSEDED로 바꾸지 않고 새 세트나 음성 작업도 만들지 않으며, `compose`는 None을 돌려준다(PR #2 리뷰·회귀 테스트).
- **완료 판정은 READY만이다.** 질문 세트는 문항과 함께 한 트랜잭션으로 READY로 쓴다. 현재 코드는 COMPOSING을 쓰지 않는다. 그래도 COMPOSING이 남아 있으면 완료로 보지 않고 SUPERSEDED로 바꾼 뒤 다시 구성한다.
- **입구는 셋이다.**
  - `compose`: `compose_questions` 작업이 부른다.
  - `begin`/`resume`/`ensure_waiting`: 음성 세션과 텍스트 API가 부른다. 함수 모양은 그대로다.
  - `submit_coding`: 코딩 최종 제출이 부른다.
- **분기는 모두 코드가 한다.** `start` 노드가 DB를 짧게 읽고 갈 길을 정한다.
- **live 질문 생성은 보이는 노드 `compose_next`다.** 지원자가 지금 질문에 답하는 동안 다음 질문을 미리 만드는 일(prefetch)은 속도 때문에 유지한다. upfront 모드에서 `compose_next`는 아무 일도 하지 않는다.
- 노드 함수는 `app/questions/steps.py`(옛 `questions/graph.py`)에 둔다.
- **코딩테스트는 별도 그래프가 아니다.**
  - 그래프는 코딩 진입(`finish` → CODING)과 종료(`coding_submit`)만 관리한다.
  - 코드 실행과 채점은 기존 coding 모듈(runner·sandbox·grading)이 한다.
  - SUBMIT은 체크포인트 없이 DB 상태만 보고 움직이므로, 체크포인트를 잃은 응시도 제출된다.
  - 그래프 호출이 실패하면 라우터가 같은 멱등 함수를 직접 부른다.
  - 마감 자동 제출(`coding_autosubmit`)은 같은 함수를 직접 부른다.

### 2. 질문 품질 검증 루프 (`app/questions/quality.py`)

`judge`는 모델을 부르지 않고 코드로 질문을 검사해 사유 코드를 돌려준다.

| 기준 | 사유 코드 |
|---|---|
| 근거 | UNGROUNDED: 이력서 인용이 원문에 없거나, 기간·학교·직함처럼 한 일이 아닌 칸이 근거이거나, 공고 근거가 공고에 없음 |
| 난이도 | TOO_LONG, MANY_TOPICS, NUMBER, COPIES_FACT, PRESUMES_EXPERIENCE, TOO_HARD(수준에 비해 어려움) |
| 유형 | NOT_MOTIVATION, NOT_JOB. 경험 슬롯은 이력서 근거 필수 |
| 명확성 | FOREIGN_SCRIPT, NESTED, NOT_A_QUESTION, FORBIDDEN |
| 중복 | DUPLICATE, SAME_BASIS(같은 근거 문장 재사용) |

`fill` 순서는 다음과 같다.

1. 요청 1 → 판정
2. 빈 슬롯이 남으면 요청 2 → 판정. 요청 2에는 떨어진 질문과 사유를 `feedback`으로 넣는다. 회사 자료 2라운드 검색 결과도 여기서 함께 쓴다.
3. 그래도 비면 코드가 만든 질문(TEMPLATE)으로 채운다.
4. 시간 초과면 요청 2 없이 바로 TEMPLATE로 간다.
5. 코드가 만든 질문(TEMPLATE)도 같은 `judge`를 통과해야 한다(`check_fallback`). 걸리면 그 영역의 고정 안전 문장(`SAFE_TEXT`, 회사·지원자 글 없음)으로 바꾼다. 그것도 안 되면 ComposeError로 명시적으로 실패한다(PR #2 리뷰 반영). 안전 문장은 직무·경험 3개, 인성·협업·동기 2개다. 한 영역의 칸 수가 이보다 많고 그 칸들이 모두 검사에 걸리면 구성이 실패한다(남은 위험).

상한과 정리한 것:

- 상한은 영역(live는 슬롯)마다 요청 2회, 모델 호출 4회(`max_model_calls`)다. 예전 최악값은 T2 5회, T3 4회였다.
- T2·T3 안의 재생성은 없앴다. T3 형식 재시도도 2회에서 1회로 줄였다.

### 3. Graph 2 — AI 평가 (`app/evaluation/graph.py`, 노드 구조 그대로)

답변 단위 판정마다 `app/evaluation/checks.py`(모델·DB 없음)가 검사한다. 검사 버전은 `unit-check-2`다.

**PR #2 리뷰 반영:** 근거 검증 실패나 이유 문장의 단어 맞추기만으로는 점수를 깎지 않는다(ADR-0023 사용자 지시). 이런 항목은 시스템 쪽으로 세고, 많으면 보류해서 담당자에게 넘긴다. '내용 부족'은 규칙 결과(짧음·무응답)와 모델 자신이 준 1~2점에서만 나온다.

| 사유 | 조건 | 재판정 뒤에도 남으면 |
|---|---|---|
| SHAPE | 항목 누락, 점수 범위 밖, 상태와 점수 불일치 | 평가 실패 → 작업 재시도 후 보류 |
| QUOTE_MISMATCH | OK 판정의 인용이 원문과 다름 | 시스템 쪽: UNLINKED, 모델 점수 유지 |
| NO_EVIDENCE | 3점 이상인데 확인된 근거 없음 | 시스템 쪽: UNLINKED, 모델 점수 유지 |
| REASON_SCORE | 이유는 '부족'인데 4점 이상 | 시스템 쪽: UNLINKED, 모델 점수 유지 |
| UNSTABLE | 표본 점수 차이 3점 이상 | 중앙값 유지, 기록만 |

- **재판정:** 문제가 있는 단위만, 사유를 피드백으로 넣어 단위당 1회 다시 판정한다(`MAX_REJUDGE=1`). T5 안에서 표본마다 하던 근거 재요청은 없앴다.
- **호출 상한:** 단위당 모델 호출 상한은 `unit_call_cap`이다. 기본(표본 3개)이면 20회이고, 넘으면 실패로 처리한다.
- **보류 기준:** 시스템 쪽 항목이 50%를 넘으면 기존처럼 보류(ON_HOLD)한다. 내용 부족은 보류하지 않는다.
- **책임 분리:** AI는 항목별 점수 후보·이유·인용만 낸다. 검증, 가중치(합 100), 총점은 서버 코드가 계산한다. `checks`와 `scoring`은 AI 클라이언트를 가져오지 않는다(테스트로 확인).
- **코딩 정답:** 정답 판정은 실제 테스트케이스 실행 결과(`sub.score`)만 쓴다. T8은 품질 점수만 낸다. T8 점수가 극단이어도 정답률이 바뀌지 않는 것과 비공개 케이스가 프롬프트·로그에 나가지 않는 것을 테스트로 확인했다.

## 결과

- **질문 쪽** (가짜 모델, 지원자 4명, 같은 스크립트로 전후 비교)
  - 최종 질문 세트 중 검사 기준을 어긴 질문: 8/36 → 0/36(시나리오 A), 4/36 → 0/36(시나리오 B)
  - 1명당 실제 모델 호출 수: 5회 그대로
  - 경험 질문 중 TEMPLATE: 0/12 → 8/12. 예전에는 기간·학교 칸을 근거로 한 질문이 그대로 나갔다.
- **평가 쪽** (가짜 모델)
  - "5점인데 이유는 부족" 판정: 재판정 1회 뒤에도 남으면 모델 점수를 유지하고 UNLINKED(시스템 쪽)로 센다. 처음 버전은 8점으로 깎았으나 리뷰 반영으로 바꿨다.
  - 근거가 연결되지 않은 단위의 모델 호출: 6회 → 4회
  - 사전 평가에서 이미 검증된 단위를 최종 평가에서 다시 부르는 호출: 최대 6회 → 0회
- **실제 GPU 모델로는 측정하지 않았다.** 실제 모델에서의 TEMPLATE 비율, 재판정 비율, 시간은 미실측이다.
- 백엔드 전체 테스트 결과는 PR에 적는다.

## 남은 위험

- **'부족' 계열 말 찾기:** 단어 목록 방식이다. 지금은 재판정 계기와 시스템 쪽 집계에만 쓰고 점수는 바꾸지 않는다. 잘못 잡으면 재판정 1회와 보류 비율에만 영향을 준다.
- **기존 평가 결과 재사용:** T5 버전이 올라 manifest가 바뀌므로, 운영 반영 뒤 기존 사전 평가 결과는 재사용되지 않는다.
- **직무 슬롯의 동기형 질문:** JOB 슬롯에 지원 동기형 질문이 와도 거르지 않는다(NOT_JOB 규칙이 좁음).
- **새 기록 키:** `detail.evidence`에 키 3개(`rejudged_units`, `unstable_items`, `check_found`)가 늘었다. 화면에는 아직 표시하지 않는다.
