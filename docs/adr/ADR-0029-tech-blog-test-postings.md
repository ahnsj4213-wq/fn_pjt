# ADR-0029 — 기존 테스트 공고 보관과 기술 블로그 기반 테스트용 가상 공고

- 상태: 채택 (2026-11-13, 사용자 지시)
- 관련: ADR-0020(회사 자료 RAG), ADR-0028(LangGraph 두 개, 구조 유지), PR #4(기술 블로그 수집기)
- 영향: 마이그레이션 0035, 공개 공고 API 필드 추가(`is_virtual`, `sources`), 운영자 공고 다시 보이기 409(`POSTING_ARCHIVED`)

## 배경

- 공고 목록에 개발 중 만든 테스트 공고가 13건 보였다. DB에는 25건이 있었다(회사 15곳).
  - "(가상)" 회사 13곳의 공고 13건: `seed_knowledge`가 만든 것
  - 개발용 회사 2곳의 공고 12건: 9건은 이미 삭제 표시
  - 지원 14건과 답변·평가 기록이 이 중 8건에 연결되어 있다.
- 질문 자료를 지어낸 회사 자료에서 실제 회사의 공개 기술 블로그 글(PR #4, 컬리·토스·카카오 각 20건)로 바꾸려 한다.
- 실제 회사 이름을 쓰므로 실제 채용공고로 오해받으면 안 된다. 또 한 회사 지원자에게 다른 회사의 글이 그 회사 사례처럼 쓰이면 안 된다.

## 결정

### 1. 기존 테스트 공고는 지우지 않고 보관한다 (`app/postings/archive.py`)

- **분류**: 공고마다 근거를 붙여 분류한다. 근거가 없는 공고(UNCLEAR)는 `--include`로 직접 지정하지 않는 한 손대지 않는다.
  - 회사명이 "(가상)"으로 끝남 → `SEED_SYNTHETIC`
  - 담당자 이메일이 테스트 전용 도메인(`.example`, `.invalid` 등)뿐임, 제목에 테스트 표기, 이미 삭제됨, 같은 회사에 테스트 제목 공고가 있음 → `TEST`
  - 기술 블로그 공고(`is_virtual`)는 대상이 아니다.
- **백업 먼저**: 공고 행 전체(`row_to_json`)와 연결 기록 수를 JSON으로 쓰고, 다시 읽어 확인한 다음에만 바꾼다. DB 전체 백업(`pg_dump -Fc`)은 운영 절차로 따로 받는다.
- **보관**:
  - `hidden_by = 'ARCHIVE'`로 바꾼다. 기존 숨김 처리를 다시 쓰므로 목록·상세·동의·지원 화면에서 모두 빠진다.
  - 열린 공고는 `CLOSED`·`close_reason = 'ARCHIVED'`로 닫는다. 지원서는 만료시키지 않는다(`service.close`를 쓰지 않음).
  - 행과 이를 참조하는 지원·답변·평가·코딩 결과는 그대로 둔다. 이미 지원한 사람은 마이페이지에서 기록을 계속 본다.
- **복원**: `--restore <백업.json>`은 보관 때 바꾼 열만 원래 값으로 되돌린다. 운영자 "다시 보이기"는 보관된 공고에 409를 낸다.
- **재생성 방지**: 보관된 공고가 있는 DB에서는 `seed_knowledge`(가상 회사)와 `scripts/seed_demo.py`(데모 회사)가 실행을 거부한다. 원래부터 두 시드는 사람이 직접 실행할 때만 돈다. 마이그레이션과 앱 시작에는 공고를 넣는 코드가 없다.

### 2. 기술 블로그 기반 테스트용 가상 공고 (`app/postings/tech_blog.py`)

- 공고 테이블은 새로 만들지 않는다. `job_postings`에 두 열을 더한다.
  - `is_virtual`: 테스트용 가상 공고 여부
  - `source_doc_ids`: 공고를 쓸 때 근거로 삼은 블로그 글
- 공고 10건(컬리 3, 토스 3, 카카오 4)은 `app/postings/data/tech_blog_postings.json`에 있다.
  - 업무·요건은 각 회사 블로그에 근거가 있는 기술로 썼고, 공고마다 근거 글 URL을 단다.
  - 블로그 원문은 저장소에 넣지 않는다. 로더가 PR #4 수집 결과 폴더에서 읽는다.
- 가상 공고임을 세 곳에서 알린다.
  - DB: `is_virtual`
  - 회사 소개 문구: "[테스트용 가상 공고] …가 게시한 채용공고가 아닙니다"
  - 화면: 배지, 안내 문단, 고용형태 "테스트용 가상 공고(채용 아님)"
- **마감일은 만들지 않는다.**
  - 가상 공고만 마감일 없이 게시할 수 있다(DB 검사 `job_postings_check`).
  - 화면에는 "테스트용 · 마감일 없음"을 보여 준다. 실제 공고처럼 보이는 "상시"는 쓰지 않는다.
  - 공고는 운영자가 닫을 때까지 열려 있다.
- 블로그 글은 `company_knowledge`에 넣는다(`origin = 'TECH_BLOG'`, `source_url` 필수, `published_at`은 블로그에 없으면 null). 500자 단위로 나누고, 공고와 무관하게 회사 전체 범위(`posting_id` NULL)로 둔다.
- **로더 검증**: 원문 파일의 `company_id`, URL 호스트, 합성 여부를 확인한다. 공고의 근거 URL이 그 회사 글이 아니면 적재를 멈춘다. 여러 번 실행해도 같은 것을 두 번 넣지 않는다.

### 3. 회사 사이 문서 혼입 0건

- 자기 회사 검색(`company_id = :c`)은 원래부터 그 회사 문서만 돌려준다.
- ADR-0020의 다른 회사 자료 빌려 오기(`shared=True`)에 두 규칙을 더한다.
  - 블로그 문서(`TECH_BLOG`)는 어떤 회사에도 빌려 주지 않는다.
  - 블로그 문서가 있는 회사는 빌려 오지 않는다.
- 꼬리질문 문서 검색(`knowledge.search`)은 원래부터 빌려 오기가 없다.

### 4. LangGraph 구조는 그대로다

- ADR-0028의 두 그래프는 바꾸지 않는다.
- Graph 1이 쓰는 입력도 그대로다. 질문은 다음을 바탕으로 만든다.
  - 지원자 이력서
  - 지원한 공고
  - 회사 문서 검색 결과(이제 블로그 글)
  - 경력 수준(`level.py`)
  - 앞선 답변과 꼬리질문 이력

## 대안

- **공고 행을 물리 삭제**: 지원·답변·평가가 공고를 참조하므로 기록이 끊긴다. 채택하지 않았다.
- **새 `archived_at` 열과 새 필터**: 기존 숨김 처리가 이미 모든 지원자 화면을 막는다. 사유 값 하나로 충분하다.
- **가상 공고에 먼 미래 마감일**: 날짜를 지어내는 것이라 지시에 어긋난다.
- **블로그 글을 공고마다 `posting_id`로 묶기**: 한 글이 여러 공고의 근거가 된다(예: 카카오 CDC 글). 그래서 회사 범위로 두고 출처만 공고에 단다.

## 위험·후속

- 회사 이름은 실제 회사다. 화면과 회사 소개에서 가상 공고임을 계속 밝혀야 한다. 공고를 외부에 공개하는 배포에는 쓰지 않는다.
- 블로그 원문의 저작권·이용약관 최종 확인은 사람이 해야 한다(PR #4). 원문은 저장소에 넣지 않는다.
- 보관 공고의 지원자는 기록을 볼 수 있지만 새 응시는 못 한다(공고가 닫힘).
