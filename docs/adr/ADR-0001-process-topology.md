# ADR-0001: 프로세스 구성과 서비스 경계 (7개 프로세스)
- 상태: 채택
- 날짜: 2026-10-27
- 작성: 에이전트 A / 통합 F
- 관련: INT-05·09·13·14·17, COD-03·06, EVL-06, SEC-03·06, NFR-8.2·8.3, AC-09·18·22, OQ-23, consolidation-round1 T1·T3·T5·T8·C1·C8

## 맥락

- 온프레미스 단일 호스트(GPU 6GB 1장)에서 동시 응시 1~2명(8.3)을 처리한다. 한 호스트에서 다음이 함께 돈다.
  - WebRTC 실시간 음성
  - 단일 LLM 공유(실시간 꼬리질문 5초, 질문 생성, 평가)
  - GPU STT·CPU TTS
  - 임의 코드 실행 샌드박스
  - 영속 평가 작업
- 1단계 설계안의 프로세스 구성은 서로 달랐다. A는 10개, B는 api·worker·runner 3개, C는 voice·tts·ai-gateway를 따로 두었다.
- 리뷰에서 인터페이스 충돌이 드러났다. 시그널링 종단 경로, 명령 채널, 하트비트 소유자가 설계안마다 달랐다.
- 실측 결과도 판단을 바꿨다.
  - S-1: Windows aiortc 동작, 서버 게이트 동작.
  - S-3: 스트림 종료로 생성 취소가 동작.
  - STT는 2초 자막을 맞추려면 GPU가 필요.

## 결정

| 프로세스 | 책임 | DB 자격 | 비고 |
|---|---|---|---|
| `app` | REST API, WebRTC 시그널링·미디어(aiortc), 면접 진행기(턴 상태 기계, 마이크 게이트, VAD 분할, 자막 이벤트), 답변 즉시 저장, 슬롯·하트비트 | 있음 | uvicorn 워커 1개. 포트 8000 |
| `worker` | 영속 작업 큐(임대·펜싱·인프라 게이트), 주기 작업, 이력서 추출·질문 구성·사전 TTS·평가·채점 오케스트레이션, PDF 파싱(자식 프로세스), 기대 출력 비교 | 있음 | `jobs.resource`별 세마포어, LLM 작업은 레인별 1개 |
| `ai` | LLM 게이트웨이(레인 RT > INTERACTIVE > BATCH, 선점), STT(GPU), TTS(CPU), 임베딩 프록시, AI 상태 탐침 | **없음** | 단일 인스턴스. 포트 8200 |
| `runner` | 샌드박스 컨테이너 실행, 자체 점검(SBX), 실행 플래그 | **없음** | Docker 소켓 단독 소유. 포트 8400 |
| `postgres` | 유일한 상태 저장소 | — | 개발 55432, 운영 5432 |
| `ollama` | LLM 서빙(GPU), 임베딩(CPU) | — | 11434 |
| `caddy` | HTTPS 종단, 정적 SPA, 보안 헤더 | — | 운영만 |

- 도메인 로직(상태 전이, 점수 계산, 범위 헬퍼)은 `backend/app` 패키지 하나에 둔다. app·worker·ai는 진입점만 다르다.
- runner는 별도 패키지다. DB 의존성이 없다.
- 클라이언트 → 서버 명령은 HTTPS로 받는다. 서버 → 클라이언트 이벤트는 데이터채널로 보낸다(T8, ADR-0009).
- app과 worker는 LLM을 직접 부르지 않는다. 항상 ai를 거친다.

## 검토한 대안 (장단점)

| 대안 | 장점 | 단점 |
|---|---|---|
| 모놀리스 1프로세스(API + 미디어 + STT + 평가) | 배포가 가장 단순 | STT·TTS가 이벤트 루프를 막는다. 평가 워커만 멈추는 AC-18 시험을 할 수 없다. Docker 소켓 권한이 API에 섞인다 |
| A 원안 10개(api·rtc·worker 2·ai-gw·speech 분리) | 장애 격리가 가장 세밀 | 시그널링·명령·하트비트를 프로세스 간에 중계해야 한다. STT가 GPU로 가면서 GPU 중재자가 둘로 갈린다 |
| B 원안 3개(api·worker·runner) | 단순 | LLM 우선순위를 전역으로 결정할 곳이 없다(실시간 호출자 app, 배치 호출자 worker). STT·TTS가 API 루프를 막는다 |
| C 원안(api 중계 + voice + tts + ai-gateway) | 미디어 격리 | api→voice SDP 중계와 명령 전달 경로가 추가된다. TTS 별도 가상환경 사유(MeloTTS)는 Supertonic 선정으로 사라졌다 |
| 도메인별 마이크로서비스 | 독립 배포 | "제출 + 평가 작업 등록" 트랜잭션이 서비스를 넘어가 7.2 누락 0을 지키기 어렵다 |

## 근거 (실측·문서·재현 가능한 위험)

- **app에 rtc를 합침**
  - STT가 ai 프로세스(GPU)로 빠지면서 미디어 쪽 CPU 작업은 Opus 디코딩·리샘플·VAD만 남았다.
  - aiortc는 Windows 네이티브에서 Opus·데이터채널·16 kHz 리샘플이 동작한다 [실측 `results-rtc-loopback.txt`].
  - 브라우저↔서버에서 게이트 이전 발화 5.46초를 서버가 폐기했다 [실측 S-1].
  - 시그널링·명령·하트비트가 한 프로세스에 있으면 중계 왕복이 없어진다.
- **ai를 단일 프로세스로**
  - Ollama에는 요청 우선순위가 없다. 선점하지 않으면 짧은 요청이 600토큰 생성 뒤에서 11.06초를 기다렸다. 스트림을 끊으면 0.49초에 처리됐다 [실측 `results-ollama-scheduling.txt`].
  - GPU 사용자가 LLM과 STT 둘이므로 중재자도 하나여야 한다.
- **ai·runner에 DB 자격을 주지 않음**
  - 모델 입출력(비신뢰)과 임의 코드 실행이라는 가장 위험한 두 경계에서 데이터 접근을 원천 차단한다.
  - 기대 출력이 runner로 가지 않으므로(C8) runner는 DB가 필요 없다.
- **worker를 분리**: 평가 서버를 멈춘 채 제출 → 재기동 후 완료(AC-18)를 프로세스 단위로 시험할 수 있다.

## 결과와 영향 (코드·스키마·운영)

- app은 uvicorn 워커 1개로 고정한다. PeerConnection과 턴 상태가 프로세스 메모리에 있기 때문이다.
  - 이벤트 루프에서 10ms 넘는 동기 CPU 작업은 금지한다(Argon2는 스레드풀, PDF 파싱은 worker).
  - 루프 지연 50ms 초과는 경고 로그로 남긴다.
- app 재시작은 진행 중 면접을 끊는다. 하트비트 만료로 INTERRUPTED가 되고 재진입(INT-11)으로 흡수한다. 배포는 응시가 없는 시간에 한다.
- worker의 LLM 작업은 레인별 동시 1개로 실행한다. 이력서 추출·질문 구성이 수분짜리 평가 뒤에서 막히지 않게 하기 위해서다. 실제 GPU 순서는 ai가 정한다(ADR-0003).
- 설정 `AIHIRE_AI_SERVICE_URL`·`AIHIRE_RUNNER_URL`·`AIHIRE_OLLAMA_URL`은 사설·루프백 주소만 허용한다(`app/core/config.py`).
- 상태 점검:
  - app은 `/api/healthz`, ai·runner는 `/healthz`·`/readyz`를 둔다.
  - app의 `/api/system/ai-health`가 ai와 runner 상태를 모아 시작 게이트(INT-14, T13)에 쓴다.
- 배포 구조는 ADR-0010을 따른다(운영 app·caddy host 네트워크).

## 남은 위험과 재검토 조건

- ai 단일 장애점: ai가 죽으면 LLM·STT·TTS가 함께 불가해진다.
  - 면접 시작 전이면 차단한다(INT-14).
  - 면접 중이면 꼬리질문을 생략하고, STT를 못 한 문항은 INT-09대로 '답변 없음'으로 저장한 뒤 진행한다(8.3).
  - ai가 살아 있고 GPU만 쓸 수 없을 때는 CPU small로 대체한다.
  - ai 재기동에는 LLM 콜드 로드 약 40초가 걸린다 [실측]. 재기동 중 끊긴 응시는 재진입(INT-11)으로 이어 간다.
- LLM 생성 중 GPU STT 지연(S-10)이 자막 2초를 넘으면 ai 안의 선점 범위를 넓힌다(ADR-0003). 그래도 안 되면 STT 전용 프로세스 분리를 재검토한다.
- 동시 응시 상한을 3 이상으로 올리거나 운영 장시간 연결이 불안정하면 미디어 처리를 별도 프로세스(또는 LiveKit)로 분리하는 안을 재검토한다.
