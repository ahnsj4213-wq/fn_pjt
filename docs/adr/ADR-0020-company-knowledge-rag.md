# ADR-0020: 회사 지식베이스 RAG를 질문 생성의 필수 경로로 삼는다

- 상태: 채택 (2026-11-05, 사용자 요구로 필수 요구사항 확정)
- 관련: QST-01, QST-03, 6.2, ADR-0005, ADR-0008, ADR-0016, ADR-0019, CLAUDE.md §0

## 맥락

지금까지 RAG는 `question_examples`에서 말투·난이도 예시를 찾는 데만 쓰였다. 질문의 내용은 공고·회사 소개·이력서에서 나왔고, 회사의 실제 프로젝트나 기술 스택은 반영되지 않았다. 직무·동기 슬롯은 질문은행을 먼저 쓰므로 은행이 충분하면 생성 자체가 일어나지 않았다.

## 결정

1. **저장**: `company_knowledge` 표에 문서를 조각 단위로 넣는다(`company_id` 필수, `posting_id` NULL이면 회사 전체). 기존 pgvector와 임베딩 모델, `index_*` 작업 방식을 재사용한다.
2. **격리**: 검색 함수 `questions/knowledge.py:search`는 회사와 공고를 인자로 받아야만 실행되고, SQL에서 범위를 건다. 복합 외래키로 다른 회사의 공고를 가리키는 조각을 DB가 거부한다. 회사별 조각이 적어 HNSW 없이 정확 검색한다(근사 색인은 범위 조건을 나중에 적용해 해당 회사 행을 놓칠 수 있다).
3. **생성 순서 변경**: 동기·직무 슬롯은 T2 생성을 먼저 하고, 실패분만 질문은행으로 채운다. 인성·협업 슬롯은 그대로 은행만 쓴다.
4. **정보 부족 처리**: 동기 슬롯에서 회사 자료가 검색되지 않으면 회사 소개도 입력에서 빼고 공고 기반 직무 질문을 만든다(`grounding.replaced = NO_COMPANY_KNOWLEDGE`).
5. **환각 차단(코드 검증)**: 인용 문장이 출처에 있어야 하고, 질문이 인용과 내용을 공유해야 하며, 출처에 없는 영문 기술명·두 자리 이상 숫자가 질문에 있으면 버린다. 회사 자료 기반 질문은 회사 내부 사정이 아니라 지원자의 판단·경험을 물어야 한다.
6. **근거 추적**: `interview_questions.grounding.sources`에 `{type, id}` 목록을 남긴다.
   - type: `KNOWLEDGE`(조각 id), `POSTING`, `COMPANY_INTRO`, `RESUME_SNAPSHOT`(지원 id와 field), `ANSWER`(답변 id), `BANK`, `POSTING_SETTINGS`
   - `grounding.retrieved`: 검색으로 입력에 들어간 조각 id
7. **이력서**: 지원 시점 스냅샷만 쓴다. 공고·회사 자료와 겹치는 항목을 `shared_terms`로 T3에 알려 먼저 고르게 한다. 질문 문장은 기존처럼 코드가 조립한다.
8. **꼬리질문**: 직전 답변 2개(각 200자), 이미 한 꼬리질문, 답변과 가까운 회사 자료 2개를 T4에 추가한다. 앵커는 현재 답변·이력서·앞선 답변에 글자 그대로 있어야 한다. 입력이 커지므로 분량을 작게 고정했다.
9. **은행 저장 제한**: 회사 자료 기반 질문은 은행에 넣지 않는다. 공고 전용 자료가 은행을 거쳐 다른 공고로 새는 경로를 막는다.
10. **가상 기업**: 실제 자료가 없어 12개 가상 기업(`data/synthetic_companies.json`, 이름에 `(가상)`, `origin = SYNTHETIC`)을 만든다. 운영 DB에 섞이지 않도록 마이그레이션·워커가 아니라 `python -m app.questions.seed_knowledge`로 사람이 직접 적재한다.

평가(T5 등) 입력과 STT·TTS·LLM 파이프라인, 점수 계산은 바꾸지 않는다. 회사 자료는 평가 프롬프트에 들어가지 않는다.

## 요구사항 충돌과 근거

| 항목 | 기존 | 변경 | 근거 |
|---|---|---|---|
| QST-01 | 질문은행의 덜 쓴 질문부터, 부족하면 AI 생성 | 동기·직무는 생성 우선, 은행은 대체 경로 | 사용자가 RAG 개인화를 필수로 확정. 은행 재사용은 대체 경로로 유지 |
| CLAUDE.md §0 | tenant 격리는 MVP 범위 밖 | 회사 ID 범위로 자료 검색 | 회사 계정·권한 체계가 아닌 검색 범위 제한이다. 기존 `company_id` 열과 담당자 권한 범위만 사용하고 멀티테넌시 추상화를 넣지 않는다 |
| ADR-0019 | 꼬리질문 입력 약 800토큰 | 입력 증가 | 대기 시간이 늘 수 있다. 실측값은 아래 검증 절 참고 |

## 대안

- 질문은행에 회사 질문을 미리 생성해 쌓기: 지원자 이력서·답변과 연결되지 않아 개인화 요구를 채우지 못한다.
- 별도 벡터 DB: 이미 있는 pgvector로 충분하고 운영 대상만 는다.
- 회사별 스키마·테넌트 분리: CLAUDE.md §0에 어긋난다.

## 유사도 하한

`rag_knowledge_min_similarity`는 0.5다. 실제 임베딩 모델 측정값(코사인 유사도):

| 검색 | 최저 | 중앙값 | 최고 |
|---|---|---|---|
| 평가 질의 → 정답 문서 (36건) | 0.555 | 0.698 | - |
| 공고로 검색, 동기 슬롯 (16건) | 0.517 | 0.578 | 0.658 |
| 공고로 검색, 직무 슬롯 (16건) | 0.522 | 0.613 | 0.650 |
| 이력서로 검색 (16건) | 0.430 | 0.490 | 0.570 |
| 답변으로 검색 (10건) | 0.428 | 0.484 | 0.649 |
| 다른 회사의 질의로 검색 (36건) | - | 0.468 | 0.616 |

처음 값 0.35는 관련 없는 자료를 거의 걸러내지 못했다. 다만 0.5에서도 관련 없는 자료가 일부 통과한다(0.616). 범위 격리는 유사도가 아니라 SQL 조건이 보장한다.

## 검증과 한계

재현 명령: `tools/eval_rag.py` (`retrieval`, `compose`, `interview`, `nodocs`). 격리·권한·근거·대체 경로의 자동 테스트: `backend/tests/test_company_knowledge.py`.

- 평가 질의는 문서를 다른 말로 바꾼 36개로, 작성자가 정답을 알고 만든 것이라 검색 정확도의 상한에 가깝다. 실제 기업 문서로 다시 재야 한다.
- 질문 품질의 합격선은 아직 정하지 않았고, 사람이 읽고 판단한 기록이다.
- 음성 경로(WebRTC·STT·TTS)가 아니라 텍스트 답변 모드로 흐름을 확인했다.
- 지식베이스 관리는 담당자 API(`/api/recruiter/knowledge`)만 있고 화면은 없다.
- 실제 기업 자료를 넣을 때의 이용 허락·기밀 등급은 정하지 않았다(OQ-41).

## 추가 결정: 가상 회사 상세 자료와 공고 초안 (2026-11-05)

- `docs/synthetic-companies/*.pdf`와 같은 글을 `app/questions/data/company_profiles/<key>.json`에 두고 `seed_knowledge`가 문서로 넣는다. PDF 파일 자체를 읽지는 않는다. 회사당 상세 문서 7개를 더한다(`COMPANY` 2, `TECH` 2, `PROJECT` 3). 프로젝트·기술 상세는 짧은 문서와 제목이 같다. PDF의 조직·입사 후 90일·FAQ는 넣지 않는다. 넣어 봤더니 입사 적응 내용이 주요 업무에 섞이고 프로젝트 문서를 검색에서 밀어내 한 회사의 동기 질문이 0개가 됐다.
- 지어낸 지표도 문서에 들어가므로 질문에 나타날 수 있다. 이 데이터는 시연·시험용이며 `origin=SYNTHETIC`으로 구분한다.
- 공고 작성 화면의 "회사 자료로 초안 작성"은 그 회사의 공고 공통 문서만 검색해 T11(`posting_draft`)로 주요 업무·자격 요건·우대 사항을 만든다. 비어 있는 칸만 채우고 저장·게시하지 않는다. 다른 공고 전용 문서는 쓰지 않는다.
- 자료에 없는 기술 이름·두 자리 이상 숫자, 경력 연수, 나이·성별 등의 조건을 담은 줄은 1회 재생성 후 뺀다.
- 가상 회사 담당자는 기본적으로 로그인할 수 없다. 시연할 때만 `python -m app.questions.seed_knowledge --demo-login <key>`로 그 계정 하나를 켠다.
- 초안 검색의 유사도 하한은 0.45다. 직무명 한 줄은 공고 전체보다 유사도가 낮다. 12개 회사의 실제 직무명은 0.473~0.589였고(하한 0.5면 4개 회사가 막힌다), 무관한 직무 5개를 회사마다 넣은 60건은 중앙값 0.396, 최고 0.484였다. 두 구간이 겹쳐서 0.45에서도 무관한 직무에 초안이 나올 수 있다. 담당자가 게시 전에 읽고 고치는 초안이라 이 위험을 받아들인다.

## 추가 결정: 생성 질문용 보정 RAG 그래프 (2026-11-06)

T2 앞뒤를 LangGraph 그래프 `app/questions/rag_graph.py`로 묶었다. `plan_queries → retrieve → generate → review`이고, 질문이 모자라면 `review`에서 `retrieve`로 돌아간다(최대 2회).

- **다중 질의:** 공고의 주요 업무 한 줄마다 검색한다. 한 줄 질의는 유사도가 낮아 하한을 0.45로 둔다. 지원 동기 검색은 공고 전체에 가까운 질의라 기존 0.5를 유지한다. 이력서도 전체 대신 문장별로 검색한다.
- **순위 결합:** 벡터 순위와 단어 일치 순위를 RRF로 합치고, 문서 제목당 1조각을 먼저 고른다.
- **검토:** 문서의 내용어 2개 이상이 질문에 없거나 이미 쓴 문서를 또 쓴 질문은 첫 회차에서 버리고, 쓰지 않은 문서로 다시 찾는다. 마지막 회차에는 이 두 규칙을 풀어 근거가 검증된 질문을 은행 질문보다 먼저 쓴다.
- **복구:** 이 그래프는 체크포인터 없이 돈다(`checkpointer=False`). 문서 원문과 DB 세션을 상태에 담기 때문이고, 복구 단위는 바깥 구성 그래프의 노드다.
- **모델 호출:** 질문 유형당 최대 2회차, 회차당 T2 재생성 포함 최대 2회라서 최악 4회다.
- **지원 동기 문장:** 프로젝트·기술 문서는 고정 문장에 제목을 넣는다. `COMPANY` 문서("회사 소개" 등)는 제목을 넣으면 문장이 어색해서, 검증을 통과한 모델 문장을 그대로 쓴다.

평가 도구: `tools/eval_question_quality.py`. 측정값은 모양만 센다. 좋은 질문인지는 사람이 읽어 판단한다.

### 측정 (2026-11-06, 가상 회사 12곳, 실제 모델, 쓰기 없음)

| 항목 | 이전 | 이후 |
|---|---|---|
| 직무 질문 생성 (36개 요청) | 24 | 36 |
| 직무 질문 0개인 회사 | 2 | 0 |
| 회사당 서로 다른 근거 문서 (평균, 최대 3) | 1.5 | 2.58 |
| 지원 동기 질문 (12개 요청) | 11 | 12 |
| 회사당 생성 시간 중앙값 | 21.1초 | 31.9초 |

- 이전과 이후의 차이에는 공고 보강, 그래프, T2 프롬프트 변경의 효과가 함께 들어 있다. 각각의 기여는 분리해서 재지 않았다.
- "구체적 내용을 담은 질문" 수(23 → 36)는 검토 노드의 규칙과 같은 기준이라 품질 증거로 쓰지 않는다.
- 사람이 읽어 본 남은 문제: 서로 관계없는 사실을 한 질문에 섞는 경우, 오탈자("정전"을 "전정"으로), 90자를 넘는 긴 질문, 같은 회사에서 비슷한 두 질문, 지어낸 내부 지표를 드러내는 질문, 기술 문서 제목이 들어간 지원 동기 문장("‘결제 서버 기술 스택’ 업무"). 합격선은 아직 없다.

## 추가 결정 (2026-11-07): 자료 없는 회사는 다른 회사 자료를 직무 사례로 쓴다

- 사용자 지시: 공고 문장만으로 질문을 만들지 말고, 이미 임베딩된 `company_knowledge`를 활용한다.
- 회사 자료가 한 건도 검색되지 않으면 `rag_graph.retrieve`가 다른 회사들의 자료를 검색한다(`knowledge.search_many(shared=True)`, 하한 0.45). 단일 관리자 MVP라 회사 간 격리 제약이 없다(CLAUDE.md §0).
- 이 자료는 `shared`로 표시하고 T2(`question_generate@1.4.0`)에 "직무 참고 사례(다른 회사, 이 회사의 사실 아님)"로 따로 준다. 질문은 가정한 상황으로만 쓰고, "귀사·우리 회사·당사" 같은 말이 들어간 질문은 버린다. 지원 동기 고정 문장에는 다른 회사 프로젝트 이름을 넣지 않는다.
- 근거 기록: `grounding.sources[].shared = true`. 지원 동기 칸은 지금처럼 `replaced = NO_COMPANY_KNOWLEDGE`.
- 실측(마이컴퍼니 "노예 구함1111", 실제 모델, 저장 없음): 직무 3개 모두 다른 회사 자료 기반(스마트밀테크, 에듀브릿지러닝, 쉴드케어보험), 지원 동기 칸 1개도 사례 기반. 지원 동기 칸이 직무 질문과 같은 자료를 고르는 경우가 있었다.

## 추가 결정 (2026-11-07): 질문은행 공통 질문도 이력서·회사 자료로 맞춘다 (T12 `question_adapt`)

- 사용자 지시: question_bank 공통 질문을 그냥 꺼내 쓰지 말고 지원자 이력서와 회사 데이터로 증강한다.
- 고르기: 인성·협업 칸은 은행 후보를 "이력서 경력·프로젝트 + 공고로 검색한 회사 자료(없으면 다른 회사 자료)"와의 임베딩 유사도 순으로 고른다(`_rank_by_relevance`).
- 맞추기: 질문 구성 그래프에 `adapt` 노드(job_skill 다음, verify 앞). 은행에서 온 질문(BANK, BANK_FALLBACK) 전체를 한 번의 T12 호출로 처리한다. 모델은 질문마다 어울리는 구절 하나만 고르고(이력서 경력·프로젝트 우선, 학력·자격증·기술 목록은 거부), 문장은 코드가 은행 질문 앞에 상황을 붙여 만든다. 회사 자료는 "~하시겠습니까?" 같은 가정 질문에만 붙인다.
- 이유(실측): 4B 모델에게 문장 전체를 쓰게 하면 근거 구절만 복사하고 질문을 잃었다(2회 모두). 구절 선택은 잘 했다.
- 검증 실패, 120자 초과, 모델 다운 → 은행 원문 그대로. 기록: `grounding.adapted_from`(원문), `basis`, `sources`, `prompt_version=question_adapt@1.1.0`. `source`는 BANK 그대로라 사용 횟수 집계는 유지된다.

## 추가 결정 (2026-11-09): 근거 하나에 질문 하나, 경력 하나에 질문 하나

실제 면접(세션 cc6a7915, 트립네스트(가상) 숙박 검색 데이터 엔지니어) 검토 결과:
직무 질문 3개가 공고 한 줄("가격 수집 실패율 감시와 원인 분석")에서 나왔고, 회사 자료 4건이 검색됐는데도 쓰이지 않았으며, 한 인턴 경력(데이터웨이브)이 이력서 질문 1개와 맞춤 은행 질문 2개에 반복됐다. 문장을 이어 붙인 어색한 질문도 있었다.

- T2 `question_generate@1.5.0`
  - 이 회사 자체 자료가 검색되면 COMPANY·JOB 질문은 자료 문장을 근거로 해야 한다. 공고 문장 근거는 첫 시도에서 거부하고 재요청하며, 재시도에서는 받는다(은행 질문보다 낫다).
  - 같은 질문 세트에서 이미 근거로 쓴 문장(`used_basis`: 앞 질문들의 `grounding.basis`와 이번 그래프에서 받은 질문)은 다시 근거가 될 수 없다. 한 번의 출력 안에서도 같은 문장은 한 번만 쓴다.
  - 프롬프트 규칙: 근거 문장 하나로만 질문을 만들고, 다른 줄의 표현을 이어 붙이지 않는다.
- T12 `question_adapt@1.2.0`
  - 다른 질문이 이미 쓴 경력·프로젝트(`compose.used_entries`, `experience[i]`·`projects[i]` 단위)는 프롬프트에 "이미 다른 질문에 쓴"으로 보여 주고, 검증에서 거부한다.
  - 한 번의 호출 안에서도 한 경력은 한 질문에만 쓴다.
  - 단, 아직 쓰지 않은 경력·프로젝트가 하나도 없으면(예: 경력 1건뿐인 이력서) 같은 경력을 다시 쓴다. 은행 원문 그대로보다 낫다.
- 이력서 질문(`_fill_resume`): 다른 질문이 쓰지 않은 경력의 후보를 먼저 고른다. 다른 경력이 없으면 같은 경력도 쓴다.
- 시험: `tests/test_question_variety.py`.

## 추가 결정 (2026-11-09): 맞춤 은행 질문에 이력서 문구를 쓰지 않는다 (T12 `question_adapt@1.3.0`)

- 사용자 지적: "규칙 기반 경보와 점검 우선순위 수립 업무를 하실 때, …"처럼 이력서 문구가 그대로 들어가 이력서를 보고 만든 질문이라는 티가 난다.
- 모델은 여전히 이력서 구절을 `basis_quote`로 고르고(코드가 원문에 있는지 확인, `grounding.basis`에 기록), 그와 별도로 그런 종류의 일을 일반적으로 표현한 상황 `scene`(6~30자, '~에서'·'~때'로 끝남)을 쓴다.
- 질문 문장 = `scene, <은행 질문 원문>`. `scene`에 숫자·%가 있거나 고른 구절과 내용어가 2개 이상 겹치거나 길이·어미가 맞지 않으면 은행 원문을 그대로 쓴다. 이력서 문구를 앞에 붙이던 방식(`polite_did`·`while_doing`)은 T12에서 쓰지 않는다.
- 실측(실제 모델, 저장 없음, 최근 지원 3건 9문항): 맞춤 6, 은행 원문 유지 3, 이력서 문구·수치가 들어간 질문 0. 예: "여러 요청을 동시에 처리해야 하는 업무에서, 원칙과 일정 사이에서 고민했던 경험과 내린 결정을 말씀해 주세요."(근거: "규칙 기반 경보와 점검 우선순위 수립"). 호출 12~13초.
- 이력서 질문(T3, 프로젝트 경험 칸)은 이력서 경험을 묻는 질문이라 그대로다.
