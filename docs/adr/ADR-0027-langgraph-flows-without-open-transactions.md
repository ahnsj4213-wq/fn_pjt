# ADR-0027: LangGraph 세 흐름 정리 — 질문 생성 하나, 면접 진행 멱등, 평가 그래프. 모델 호출 중 트랜잭션 없음

- 상태: 채택 (2026-11-10). 운영 반영(api·worker 재빌드)은 사용자 결정 대기다.
- 근거: 사용자 지시 2026-11-10 (LangGraph 아키텍처 리팩터링)
- 관련 ADR: ADR-0016(면접 진행·질문 구성 그래프), ADR-0020(회사 자료 RAG), ADR-0022(live 생성), ADR-0006(평가 작업), ADR-0023(평가 신뢰성)
- 바뀌지 않는 것:
  - API·DB 스키마. 리포트 `detail`에 JSON 키 `evidence`만 추가한다.
  - 작업 큐 구조: `jobs` 테이블이 기록, Celery·Redis가 전달.
  - live 기본값과 다음 질문 미리 계산(ADR-0022 후속).
  - 질문 세트 불변 스냅샷, TTS 사전 합성.
  - T5 3회 중앙값, 루브릭과 서버 집계 규칙, 시도 2회 후 ON_HOLD(EVL-06).

## 배경

- 개선 전 질문 생성은 모델 호출 80회를 DB 트랜잭션이 열린 채 실행했다. 트랜잭션은 최대 27.3초 유지됐다(측정 1). `idle_in_transaction_session_timeout` 30초에 근접한다.
- RAG 하위 그래프는 영역마다 최대 8회 LLM과 10회 임베딩을 썼다.
- 면접 진행은 같은 단계가 다시 실행되면(크래시 후 재개, 두 번째 resume) 꼬리질문을 다시 판단하거나 동시 쓰기에서 IntegrityError가 날 수 있었다.
- 최종 평가는 일반 함수 순서(`pipeline.build_report`)였다. 재시도 때 끝난 단계도 처음부터 다시 실행했다.

## 결정

### ① 질문 생성: 그래프 하나 (`questions/graph.py`)

- 호출자는 `questions.graph.run(application_id, settings_id)`만 쓴다.
- 노드 흐름: `plan(코드) → project(T3) → motivation(T2+RAG) → job_skill(T2+RAG) → write`
- 상태: `application_id, settings_id, live, picked, qset_id`
- 회사 자료 RAG(`rag_graph.py`)는 LangGraph 하위 그래프가 아닌 함수 루프다.
  - 루프 상태에는 문서 원문과 AI 클라이언트가 들어가 체크포인트에 넣으면 안 된다.
  - 복구 단위는 이 함수를 호출하는 노드다.
  - 최대 2라운드. 2라운드는 새 문서를 찾았을 때만 돌고, 내부 재생성은 하지 않는다(`last_chance`).
- 검증 실패 시 실패한 질문만 다시 만든다.
  - 재생성 메시지에 질문 번호별 실패 코드를 담는다. 통과한 질문은 고정한다.
  - 재생성은 1회까지다. 그래도 모자란 칸은 코드가 만든 대체 질문(이력서 경험·공고 기반, `source=TEMPLATE`)으로 채운다.
- 검증 항목: 유형(`level.fits_type`), 수준·난이도, 근거(인용 일치·복사 금지), 중복·같은 근거.
  - 명확성 규칙(qc-1, 신규): `FOREIGN_SCRIPT`(한자·가나 등), `NESTED`(물음표·조건 2개 이상).
  - 버려진 질문은 코드별 개수로만 로그에 남긴다(`question_reject`). 원문은 남기지 않는다.
- 프롬프트 버전: T2 `question_generate@1.8.0`(형식 재시도 1회), T3 `resume_question@1.6.0`.
- 질의 벡터를 한 번 만들어 검색과 예시 검색이 함께 쓴다.

### ② 면접 진행: 같은 단계가 다시 돌아도 효과는 한 번

- `decide_followup`
  - 이미 `followup_decisions`가 있으면 모델을 부르지 않고 기존 결과를 돌려준다.
  - 쓰기 트랜잭션에서 본질문 행을 잠그고 다시 확인한다.
- `transcribe`: `finalize`가 None이면(이미 확정됨) 기존 답변 id를 쓴다.
  - 답변 1개, `pre_evaluate` 1건만 남는다.
- live 질문 생성: 읽기 → 트랜잭션 밖 생성 → 짧은 쓰기의 3단계다.
  - 쓰기 트랜잭션은 `pg_advisory_xact_lock(live:<app>)`을 잡고 상태·세트·순번을 다시 확인한다.
  - 같은 프로세스 안에서는 앱별 `asyncio.Lock`으로 미리 계산과 즉시 생성을 차례로 실행한다.

### ③ 평가 그래프 (`evaluation/graph.py`, `thread_id = eval:<application>:<job>`)

```
prepare → unit(단위 하나씩, 순차) ↺ → verify → code_review(T8) → custom → score(코드) → summary(T6) → feedback(T7)
그 뒤 핸들러: finalize(점수 재계산 일치 확인) → 펜싱 트랜잭션 저장 → 체크포인트 삭제
```

- **prepare**
  - 사전 평가(`answer_pre_evaluations`)를 읽는다. 실행 중인 `pre_evaluate`는 최대 45초 기다린다.
  - 재사용 규칙(`units.reuse_problems`)에 걸린 단위만 재평가 목록에 넣는다. 규칙: `SHAPE`, `RUBRIC_VERSION`, `STALE`, `QUOTE_MISMATCH`, `UNLINKED`(3점 이상인데 인용 없음). 프롬프트·모델 버전은 manifest_hash로 확인한다.
- **unit**
  - 단위 하나를 T5로 평가한다(3회 중앙값).
  - DB 저장을 먼저 하고 체크포인트를 남긴다. 그 사이에 죽으면 다음 실행이 `run_ref`로 저장된 결과를 찾아 모델을 다시 부르지 않는다.
- **verify**: 실패 종류를 나눠 센다.
  - 시스템 실패: `UNLINKED`, `QUOTE_MISMATCH`, `NO_EVIDENCE`
  - 내용 부족: `LOW_CONTENT`, `TOO_SHORT`, `NO_ANSWER`
  - 시스템 실패가 판정 항목의 50%(`SYSTEM_HOLD_RATIO`)를 넘으면 `EvidenceUnverifiable`(ON_HOLD)이다.
  - 내용이 부족한 답변은 보류하지 않고 낮은 점수로 끝난다.
- **점수와 판단**: 점수·근거·코멘트는 모델이 정한다. 서버는 형식·범위·인용 검증과 확정된 집계(가중치 합 100)만 한다.
- **버전 일관성**
  - 시도 사이에 manifest가 바뀌면 스레드를 지우고 처음부터 실행한다.
  - 실행 도중 바뀌면 `ManifestChanged`가 나고, 핸들러가 시도를 쓰지 않는 지연으로 처리한다. 서로 다른 버전이 한 리포트에 섞이지 않는다.
- **결과 기록**: 리포트 `detail.evidence`에 판정 수, 실패 종류별 수, 재사용·새 평가·재평가 수를 남긴다.

### 재시도 책임

| 층 | 무엇을 | 상한 |
|---|---|---|
| `run_task` (노드 안) | 형식 재시도, 검증 실패 재생성 | 형식 2(T2는 1), 재생성은 작업별 `regen_limits` |
| 그래프 | 자체 재시도 루프 없음. 실패한 노드에서 멈춤 | — |
| `jobs` (DB 큐) | 작업 재시도. 같은 job id라 같은 스레드를 이어서 실행해 끝난 노드는 다시 부르지 않음 | 작업별 `max_attempts`, 인프라 장애는 시도 미소모 |
| Celery | 전달만. 재시도하지 않음 | — |
| 담당자 재평가 | 새 job, 새 스레드. 유효한 단위 결과는 재사용 | — |

### 트랜잭션

- 모든 노드는 짧은 `session_scope`로 읽고 닫은 뒤 모델을 부른다. 쓰기도 별도의 짧은 트랜잭션이다.
  - 검색처럼 세션을 받는 함수에는 `questions/dbio.ShortReads`(문장마다 짧은 트랜잭션, 쓰기 거부)를 넘긴다.
- `core/db.open_scopes()`로 열린 트랜잭션 수를 센다. 테스트는 모든 LLM·임베딩 호출 시점에 0인지 확인한다.
  - 대상: 질문 upfront·live·RAG, pre_evaluate, 평가 그래프 전체.
- 코딩 문제 변형(`problem_rewrite`)도 트랜잭션 밖에서 부른다.

### 체크포인트와 업무 데이터

- 업무 DB가 진실이다. 노드는 이미 DB에 있는 결과를 먼저 찾고, 있으면 모델을 부르지 않는다.
- 상태에는 id·코드·개수·점수만 둔다.
  - 평가 그래프는 답변 원문·인용 문장 대신 위치만 둔다. 체크포인트 바이트 검색 테스트로 확인했다.
  - 질문 그래프의 `picked`에는 질문 문장과 이력서 근거가 남는다. 실행이 끝나면 지운다(남은 위험).
- 정리: 끝난 스레드는 `forget()`으로 지운다. `purge_finished`는 실행 중이 아닌 `compose:`·`eval:` 스레드와 끝난 면접 스레드를 지운다.

## 측정 (같은 조건)

- 조건
  - 실제 모델 qwen3.5:4b, `eval_samples=3`.
  - `aihire_qe2e` 복제본을 최신 마이그레이션으로 올린 DB. 지원 3건, 질문 생성 upfront 2회 반복, 평가 2건.
  - 측정 도구: 일회용 스크립트(측정 뒤 삭제). 작업별 LLM 호출·재시도·소요 시간·트랜잭션 유지 시간을 기록했다.
  - 개선 전 코드는 리팩터링 직전 `backend/app` 사본이다.

## 남은 위험

- 질문 그래프 체크포인트에 질문 문장·이력서 근거가 실행 동안 남는다. 실행 종료 시 삭제한다.
- 여러 API 프로세스가 같은 live 칸을 동시에 만들면 GPU 생성이 중복될 수 있다(행은 1개만 남는다).
- `SYSTEM_HOLD_RATIO=0.5`, `NESTED`/`FOREIGN_SCRIPT` 오탐률, UNLINKED 재평가의 효과는 더 많은 실측이 필요하다.
- 보류 판정은 결정적이다. 두 번째 시도도 같은 결론이라, 다시 실행하는 길은 담당자 재평가뿐이다.
- health manifest가 비어 있으면 평가를 지연한다(이전에는 실행). EVL-08 버전 기록을 지키기 위한 변경이다.
