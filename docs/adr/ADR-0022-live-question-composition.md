# ADR-0022: 본질문을 면접 중에 한 문항씩 생성한다 (QST-02 변경)

- 상태: 채택 (2026-11-07, 사용자 결정)
- 관련 요구사항: QST-02(P0, 변경), QST-01·03·05·06·07, INT-04, AC-07, AC-12

## 배경

PRD QST-02는 "면접 시작 전 본질문 10개 구성"이다. 사용자 지시(2026-11-07): "질문 구성은 최초 면접 시작하기 전에 10개 한번에 다 만들지
말고, 첫 질문만 생성하게 해. 그 뒤의 질문들은 면접자 답변에 따라 증강시킨 질문들을 실시간으로 생성하게 해."
선택지로 (1) 완전 실시간, (2) 미리 만들고 직전에 다시 증강하는 혼합, (3) 보류를 제시했고, 사용자가 (1)을 골랐다.

## 결정

- 면접 시작 전(`compose_questions` 작업): 질문 계획(유형별 칸, 커스텀 문구)을 `question_sets.plan`(migration 0032)에 저장하고 첫 본질문만 쓴다.
- 면접 중: 면접 진행 그래프의 `decide_followup` 뒤와 `present` 앞에서 `app.questions.live.ensure_next`가 다음 칸을 만든다.
  열린 질문(꼬리질문 포함)이 하나라도 남아 있으면 만들지 않는다. 신청별 advisory lock 안에서 다시 확인하므로 중복 생성이 없다.
- 생성 재료는 기존과 같고(질문은행+T12 맞춤, T3 이력서, T2+RAG 그래프), 직전 답변 2개(각 400자)가 더해진다.
  답변은 회사 자료 검색 질의, 이력서 질문의 우선 항목(`shared_terms`), 질문은행 후보 순위에 쓰인다.
- 실패·지연(45초, `AIHIRE_LIVE_COMPOSE_TIMEOUT_SECONDS`) → 같은 유형의 질문은행 질문(`BANK_FALLBACK`).
- 설정 `AIHIRE_QUESTION_MODE=live|upfront`(기본 live). upfront는 PRD 원래 방식이며 되돌리기 경로다. 기존 테스트는 upfront로 돈다.

## 유지되는 것

- 유형별 개수와 순서(계획에서 온다), 질문 행의 불변성(QST-06: 한 번 쓴 행은 바뀌지 않는다), 꼬리질문 규칙(AC-12), 근거 기록.

## 영향과 위험

- 질문 사이 대기: 6GB GPU에서 문항당 약 7~15초(T2·T3·T12 실측 기반 추정, 면접 흐름 실측 아님). 화면 대기 문구를 "다음 질문을 준비합니다"로 바꿨다.
- 사전 TTS 합성은 첫 질문만 된다. 이후 질문은 기존 대체 경로(제시 시 합성)를 쓴다.
- 면접 중 모델 부하가 늘어 동시 응시 한도(INT-13)에 영향이 있다. 미측정.
- 같은 공고 지원자끼리 받는 질문 차이가 커진다(공정성). 유형별 개수와 루브릭은 같다.
- 면접 도중 중단되면 질문 행은 답한 데까지만 남는다(리포트의 본질문 수도 그만큼).


## 후속 (2026-11-09)

ADR-0025로 기본값이 `upfront`로 바뀌었다. live 모드는 `AIHIRE_QUESTION_MODE=live`로 남는다. 6 GB GPU에서 면접 중 본질문 생성이 질문 전환을 10~40 s 지연시켰기 때문이다.

## 후속 (2026-11-10, 사용자 결정)

ADR-0025가 기본값을 `upfront`로 바꾼 것은 11-09 지시 10·11번("기본 질문은 면접 준비 단계에서 미리 생성")을 이 ADR의 11-07 결정을 뒤집는 것으로 해석한 결과였다.
두 지시가 충돌한다는 확인을 받지 않았다. 사용자가 11-07 결정을 다시 확인하고 "live + 미리 계산"을 골랐다.

- 기본값을 다시 `live`로 한다(`core/config.py`, compose `QUESTION_MODE`).
- **미리 계산**: 본질문 N이 화면에 나오는 순간(`interview/graph.py` present 노드) 본질문 N+1을 백그라운드에서 만들기 시작한다(`live.prefetch` → `ensure_next(ahead=True)`).
  - 지원자가 N에 답하는 동안 생성이 끝나므로 전환 대기가 줄어든다.
  - N+1은 N-1까지의 답변으로 만들어진다. N의 답변은 꼬리질문(T4)이 바로 반영한다.
  - 답변 후 `ensure_next`는 이미 쓰인 질문을 찾거나, 같은 advisory lock에서 진행 중인 생성을 기다린다. 두 번 만들지 않는다.
  - 질문이 쓰이면 바로 음성 합성 작업(`tts_pregen`, 문항별 dedupe)을 등록한다.
  - 생성 트랜잭션만 유휴 제한을 120 s로 늘린다(`SET LOCAL`). 모델 호출이 lock을 쥔 트랜잭션 안에서 돌기 때문이다.
- 미측정: 실제 GPU에서의 전환 시간, 답변 중 생성(T2/T3)과 꼬리질문 판단(T4)이 GPU를 함께 쓸 때 T4 지연.
