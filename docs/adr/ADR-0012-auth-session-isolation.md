# ADR-0012: 인증·세션·CSRF·회사 격리
- 상태: 채택 — 가입 중복 이메일 처리(OQ-34)만 채택(임시)
- 날짜: 2026-10-27
- 작성: 에이전트 E / 통합 F
- 관련: USR-01~07, SEC-03·04·05, ADM-07, AC-01~05·19, R-15·16, OQ-34, consolidation-round1 T1·T21·T25, ADR-0011, TRD `07-security.md` 3~5절

## 맥락

- 사용자는 지원자와 담당자 두 역할이고, 담당자는 회사별로 운영자가 발급한다(USR-03). 담당자는 "다른 회사 데이터를 어떤 경로로도 볼 수 없어야" 한다(2.3, SEC-03).
- 로그인 실패 문구로 계정 존재를 알 수 없어야 하고(USR-04), 세션은 마지막 요청 후 2시간 유지한다(USR-06).
- SPA와 API는 같은 출처(caddy 뒤)이고, WebRTC 시그널링도 같은 `app` 프로세스에 있다(T1).
- 회사 간 누출(R-15)과 지원자에게 내부 채점 정보 누출(R-16)이 출시 차단 위험이다.

## 결정

1. **비밀번호**: Argon2id(argon2-cffi 기본, m=64 MiB·t=3·p=4), 스레드풀 계산, 동시 해시 세마포어 4. 없는 계정은 같은 파라미터의 더미 해시로 검증한다.
2. **로그인 실패**: 없는 계정·비밀번호 불일치·역할 불일치·비활성을 401 `AUTH_FAILED` 한 가지로 응답한다. 역할·상태 비교는 해시 검증 뒤. OPERATOR는 웹 로그인 불가.
3. **무차별 대입 제한**: HMAC(정규화 이메일) 키 15분 5회, IP 키 15분 30회 실패 시 15분 429. 존재하지 않는 이메일에도 같은 카운터. 카운터는 DB. 운영은 프록시 헤더로 실제 클라이언트 IP를 쓴다.
4. **세션**: 서버 세션. 쿠키에는 256비트 불투명 토큰, DB에는 SHA-256만. 로그인마다 새 토큰(고정 공격 차단), 유휴 2시간 슬라이딩(60초 단위 갱신), 절대 수명 없음, 로그아웃은 행 삭제, 비밀번호 변경·탈퇴·비활성 시 전 세션 삭제.
5. **쿠키**: HttpOnly, SameSite=Strict, Path=/, 만료 미지정. 운영은 Secure 필수(기동 검사)와 이름 `__Host-aihire_sid`, 개발 localhost는 Secure 해제 허용.
6. **CSRF**: 동기화 토큰(세션 행)을 로그인 응답·`GET /api/auth/me`로 주고 POST·PUT·PATCH·DELETE에 `X-CSRF-Token`을 요구한다. 함께 Origin 검사(`trusted_origins`). 로그인·가입은 Origin 검사 + JSON 전용 본문. 시그널링도 같은 의존성을 쓴다.
7. **역할 가드**: 비로그인 401, 역할 불일치 403 `ROLE_FORBIDDEN`(USR-05 안내 문구). 담당자도 공개 공고 GET은 가능하고 지원 API는 403(T21).
8. **회사·소유자 격리(앱 레벨, P0)**: 모든 라우트에 정책 메타데이터(role·scope·resource) 선언, 담당자 리소스는 `get_for_company`, 지원자 리소스는 `get_for_owner`로만 조회. 없거나 범위 밖이면 같은 404 `NOT_FOUND`. company_id는 세션 값만. 복합 FK `(id, company_id)`로 자식·부모 회사 불일치를 DB가 막는다. 담당자 모듈 원시 SQL 금지(정적 검사).
9. **DB 권한**: 앱 롤은 테이블 소유자가 아니고(마이그레이션은 소유자 롤), app 롤은 공개 예시 뷰로만 테스트케이스를 보며, `decision_status`는 worker 롤에 칼럼 권한이 없다. `ai`·`runner`는 DB 자격이 없다.
10. **지원자 응답**: 지원자 전용 화이트리스트 스키마, `candidate_feedback` 별도 테이블, `PublicPosting`, 데이터채널 메시지 키 허용목록. 검사 범위는 지원자 세션이 받는 모든 응답(QG-02).
11. **RLS**: P0에서는 쓰지 않는다. `applications`·`recruiter_reports`·`recruiter_notes` 시범 적용은 P1 선택.
12. **가입 중복 이메일(OQ-34, 임시)**: 409 `EMAIL_UNAVAILABLE` "사용할 수 없는 이메일입니다." + 가입 IP 속도 제한. 메일 인증 가입은 후속.

## 검토한 대안 (장단점)

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| JWT(서명 토큰) | 무상태 | 즉시 무효화·역할 변경 반영에 차단 목록이 필요, 슬라이딩 2시간 구현 복잡, localStorage면 XSS 노출 | 기각 |
| SameSite 쿠키만으로 CSRF 방어 | 단순 | 형제 서브도메인 요청, Lax의 최상위 GET | 기각(보조로만) |
| 이중 제출 쿠키 CSRF | 서버 상태 불필요 | 서브도메인 쿠키 주입에 약함 | 기각 |
| PostgreSQL RLS를 P0 격리 수단으로 | 앱 실수에도 DB 차단 | 트랜잭션마다 설정, 소유자·superuser 우회, worker·통계 경로 별도 정책, 디버깅 난도 | P1 선택 |
| 회사별 스키마·DB | 강한 분리 | 질문은행·통계·마이그레이션 복잡 | 기각 |
| 다른 회사 리소스에 403 | 원인 명확 | 존재가 드러남 | 기각(404 동일성) |
| 세션 절대 수명 12시간(E 제안) | 탈취 세션 수명 제한 | PRD는 유휴 2시간만 규정 | 미채택 |

## 근거 (실측·문서·재현 가능한 위험)

- 구현·시험(`backend/tests/test_auth.py`, `test_postings_apply.py`): 로그인 실패 동일성, 존재 무관 스로틀, 쿠키 HttpOnly·해시만 저장, CSRF·Origin 거부, 2시간 유휴 만료, 담당자 지원 403, 다른 회사 공고 404와 없는 ID 404의 구별 불가.
- 재현 가능한 위험: 교차 사이트 요청 하나로 진행 중 면접 연결을 끊는 공격(D-06) — 시그널링에도 CSRF·Origin을 적용해 막는다. 공고 모델 통째 직렬화 시 가중치·커스텀 질문 노출(D-08) — `PublicPosting`로 막는다.
- 구현 확인 중 발견한 운영 위험: 리버스 프록시 뒤에서 `request.client.host`를 쓰면 모든 사용자가 같은 IP 키를 공유해 30회 실패로 전체 로그인이 막힌다(07 G-05).

## 결과와 영향 (코드·스키마·운영)

- 구현됨: `app/auth/passwords.py`, `sessions.py`, `throttle.py`, `deps.py`, `router.py`, `core/errors.py`(동일 404), `sessions`·`auth_throttle` 테이블, 복합 FK, 운영 기동 검사 일부, 운영 OpenAPI 비활성.
- 남은 구현(07 14절): 운영 쿠키 이름 `__Host-` 접두어, CSRF 상수 시간 비교, 스로틀 HMAC 키 설정화, 프록시 헤더 신뢰, 가입 속도 제한, 재해시, 라우트 정책 메타데이터·범위 헬퍼·인벤토리 테스트, DB 롤 분리와 권한, TrustedHost, 전 세션 무효화 호출부.
- 프런트: 모든 상태 변경 요청에 `X-CSRF-Token`, 로그인·401 뒤 토큰 재수령, 화면 가드는 안내용.
- 운영: uvicorn `--proxy-headers --forwarded-allow-ips=127.0.0.1 --no-access-log`, 운영 비밀(스로틀 키 등)은 compose secrets.

## 남은 위험과 재검토 조건

- 가입 API는 중복 이메일을 알릴 수밖에 없다(OQ-34). 메일 인증 기반 가입을 도입하면 결정 12를 바꾼다.
- 계정별 잠금은 공격자가 특정 사용자의 로그인을 15분 막을 수 있게 한다(가용성). 신고가 생기면 지연 증가형 제한으로 바꾼다.
- 앱 레벨 격리는 헬퍼를 우회한 쿼리 한 줄로 뚫릴 수 있다. IDOR 매트릭스(08 6절)가 실패하거나 원시 SQL 예외가 늘면 RLS를 P0로 당긴다.
- 운영 도메인이 서브도메인을 다른 서비스와 공유하면 SameSite·`__Host-` 가정과 HSTS includeSubDomains를 다시 검토한다.
