# ADR-0006: 상태 기계, 영속 작업 큐, 평가 재시도, 점수 계산

- 상태: 채택(임시), **작업 분배(대기·집기)는 ADR-0013(Redis)으로 대체**(2026-10-29). 영속 기록·펜싱·재시도·상태 기계는 이 문서 그대로 — 표 밖 전이(OQ-25·26), 진행 중 응시와 마감(OQ-27), 결정 복귀 불허(OQ-28)는 팀 확인이 필요하다
- 날짜: 2026-10-27
- 작성: 에이전트 B / 통합 F
- 관련: PRD 7.1~7.4, 6.4·6.5, EVL-04·05·06·08, INT-12·13, COD-05, NFR-8.3, AC-17·18·20·21 / OQ-05·06·07·10·11·15·16·21·23·25~28 / consolidation C7, T10, T14~T19, T23, T24
- 구현: `backend/migrations/versions/20261027_0001_initial.py`(스키마·트리거·`TRANSITIONS`·`PERIODIC`), `app/jobs/queue.py`(`JOB_KINDS`, `enqueue`), `app/applications/lifecycle.py`. 상세는 TRD 03.

## 맥락

- PRD 7장은 지원 건 하나가 응시·평가·채용 결정 세 상태를 **따로** 갖도록 정했다. 7.2는 "제출과 같은 트랜잭션으로 평가 작업을 기록하고, 서버가 재시작돼도 사라지지 않으며, 실패를 끝 상태로 두지 않는다"를 요구한다.
- EVL-06은 실패나 10분 초과 때 자동 재생성을 1회 하고, 다시 실패하면 '평가 보류'로 둔 뒤 담당자 재평가를 요구한다. AC-18은 "평가 서버를 멈춘 채 제출해도 다시 켜면 평가 완료까지 간다"이다.
- 위험은 세 가지다. 평가 작업이 중복 실행되거나 좀비 작업이 결과를 두 번 쓰는 것(R-14), LLM이 꺼진 동안 재시도 횟수가 소진되는 것(OQ-23), 점수 반올림 순서에 따라 총점이 달라지는 것(OQ-10, AC-17)이다.

## 결정

1. **상태 3칼럼 + 허용 전이 표 + 트리거**
   - `applications`에 `attempt_status`·`eval_status`(NULL = 평가 없음)·`decision_status`를 둔다.
   - 허용 전이는 `state_transitions` 시드 하나로 정하고 서비스 코드도 같은 표를 쓴다. 서비스는 조건부 `UPDATE … WHERE 칼럼 = ANY(:from)`으로만 바꾼다.
   - `guard_application` 트리거가 불허 전이를 `AP001`로 막고 이벤트를 기록한다. 교차 불변식(평가 완료 전 결정 불가 등)은 CHECK로 둔다.
2. **PRD 7.1 표 밖 전이를 임시로 둔다**
   - INTERRUPTED → SUBMITTED: 코딩 중 끊긴 채 마감되면 자동 제출(COD-05, OQ-25).
   - READY/PREPARING → EXPIRED: 공고 마감(OQ-26).
   - INTERVIEWING·CODING은 마감돼도 끝까지 진행하고, 새 시작·재개만 막는다(OQ-27).
   - 평가 RUNNING → PENDING은 작업이 큐로 돌아갈 때 쓴다(OQ-23).
   - 결정을 '검토 전'으로 되돌리는 전이는 없다(OQ-28).
3. **동시 응시 슬롯**
   - INTERVIEWING만 점유한다. 시작·재개 때 전역 advisory lock 안에서 개수를 세고 확보한다.
   - CODING 진입·제출 때 반환하고, INTERRUPTED는 120초 유예 뒤 반환한다(T10).
   - CODING의 생존 신호는 코딩 API와 30초 하트비트이며, 120초 무응답일 때만 INTERRUPTED가 된다(C7).
4. **영속 작업 큐 = PostgreSQL `jobs` 테이블**
   - 등록: 상태 변경과 같은 트랜잭션에서 하고(`enqueue`), `dedupe_key` 부분 유일 인덱스로 중복을 막는다. `pg_notify`로 깨운다.
   - 집기: `FOR UPDATE SKIP LOCKED`로 집되, 상태 탐침이 OK인 자원(`resource`)의 작업만 집는다(OQ-23).
   - 임대·펜싱: 임대 60초 + 하트비트 15초. 펜싱 토큰은 전역 시퀀스 `job_lease_token_seq`다. 결과 반영은 `WHERE lease_token = :tok AND state='RUNNING'` 조건부로 하고, 0행이면 롤백한다.
   - 중간 결과는 자기 `run_id`에만 쓴다. 최종 리포트는 PK가 지원 건이라 두 번 쓸 수 없다.
5. **시도 횟수**(T16)
   - 시도 시간 10분은 **임대 시작부터** 잰다. 평가 작업은 최대 2회(첫 시도 + 자동 재생성 1회)이고, 소진하면 FAILED와 eval ON_HOLD를 같은 트랜잭션에서 쓰며 점수 행은 만들지 않는다.
   - **인프라 오류**(연결 거부·503·탐침 실패)와 **임대 상실**(워커 사망, 3회까지)은 시도로 세지 않는다. ai 게이트웨이의 선점(PREEMPTED)은 시도 안의 재요청이다.
   - 재평가(ADM-06)는 새 작업이다(ON_HOLD → PENDING).
6. **선평가**(T15): 답변을 확정할 때 `pre_evaluate`(BATCH)를 등록한다. 최종 평가는 manifest가 같은 단위 결과(`answer_pre_evaluations`)를 재사용한다. 우선순위 표기는 P1 그대로다.
7. **점수**(T18·T19)
   - 답변×항목 1~5는 LLM이 판정하고, 나머지는 모두 서버 코드가 `Decimal`로 계산한다.
   - 문항 점수 = 본·꼬리 평균. 항목 점수 = (Σ 문항 / N) × 20 → 0.01 HALF_UP 저장. N은 SUBMITTED면 10, EXPIRED면 확정 답변이 있는 본질문 수(OQ-07).
   - 코딩 = 통과 / 전체 × 100 → 0.01.
   - **총점은 저장된 항목·코딩 점수로** Σ(점수 × 가중치 / 100)를 계산해 0.01 단위로 반올림한다. 화면은 소수 첫째 자리다.
   - '근거 부족'과 '답변 없음'은 둘 다 1점이고, **개수는 따로 센다**(`insufficient_count`, `no_answer_count`).
   - 가중치는 첫 INTERVIEWING 진입 때 잠기고(OQ-05), 지원 건에 `eval_settings_id`로 고정된다.
8. **불변 기록**
   - 출제 질문·답변·평가 행·가중치 버전은 수정·삭제 금지이고, 보관 삭제(`app.purge`)만 예외다.
   - 동의·결정 이력·감사 로그는 우회가 불가능한 엄격 불변이다(T14).
9. **주기 작업**은 `periodic_tasks` 행 갱신으로 한 worker만 실행하고, 본문은 멱등이다: reaper 15초, sweeper 30초, 코딩 자동 제출 15초, 공고 자동 마감 60초, 보관 삭제·파일 정리·세션 정리 1시간.

## 검토한 대안 (장단점)

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| 상태 1칼럼(B PRD의 SUBMITTED~REPORT_READY) | 단순 | PRD 7장이 명시적으로 버렸다. 평가 실패가 응시 기록을 흔든다 | 기각 |
| 상태 이벤트 테이블만(이벤트 소싱) | 이력 완전 | 현재 상태 계산 비용, 교차 CHECK 불가 | 기각(이벤트 테이블은 보조로 둠) |
| Redis + Celery/RQ | 생태계 | DB 커밋과 등록이 원자적이지 않아 outbox가 필요. 구성요소 +1, Celery는 Windows 비공식, 오프라인 반입 +1 | 기각 |
| Procrastinate(PG 기반 라이브러리) | 같은 트랜잭션 등록 | 자원 게이트(OQ-23)·펜싱·10분 시도 제한을 밖에서 덧대야 한다 | 기각 |
| 작업마다 `run_no`로 펜싱(A 1단계안) | 이해 쉬움 | 재평가는 새 작업이라 번호가 1로 돌아가 옛 좀비와 충돌 | 전역 시퀀스 채택 |
| 인프라 오류도 시도로 셈 | 구현 단순 | LLM이 꺼진 동안 2회가 금방 소진돼 AC-18을 담당자 조작 없이 못 지킨다 | 기각 |
| 총점을 반올림 전 값으로 계산 | 수학적으로 더 정확 | 화면·리포트 값으로 같은 총점을 재현할 수 없어 AC-17 판정이 흔들린다 | 기각 |
| 슬롯을 CODING도 점유(OQ-15 원안) | 원안 그대로 | 상한의 원인(GPU·STT)과 무관. 끊긴 코딩 응시자가 상한 때문에 재진입을 못 하면 서버 시계로 흐르는 시간을 잃는다 | 기각(T10) |

## 근거

- 실측(`prototypes/README.md`): 문항 평가는 답변당 6~11초로, 14답변 순차 처리가 약 1.4~2.6분이다. 10분 시도 제한은 충분하지만 3분 목표(8.2)는 선평가 없이 경계선이다. 스트림을 끊으면 생성이 0.49초 만에 취소되므로 선점이 가능하고, 선점은 시도로 세지 않는다.
- 재현 가능한 위험(B 1단계안 6절, 리뷰 R-08·R-16): 좀비 워커 이중 기록, 재평가 후 run 번호 충돌, 마감 공고에 READY가 영구히 남는 문제, 코딩 중 끊긴 건의 자동 제출 불가.
- PRD 문장: 7.2 "평가 실패를 끝 상태로 두지 않는다", 6.4 "근거 부족"과 "답변 없음"을 따로 정의, 6.4 "첫 응시 후 가중치 잠금 → 재계산 없음".

## 결과와 영향

- 스키마: TRD 03 2·4·7·9절. 코드: 큐 등록과 종류 표는 `app/jobs/queue.py`, 공고 마감 처리와 평가 등록은 `app/applications/lifecycle.py`.
- 운영: worker를 재시작해도 따로 복구할 것이 없다(기동 직후 reaper 1회). 오래 걸리는 작업은 `jobs`와 `evaluation_runs`로 조회한다(CLI `requeue-evaluation`).
- 테스트(T-STATE-7.1·7.2, AC-17·18):
  - 모든 (from, to) 조합을 직접 UPDATE해 불허 전이가 `AP001`인지 확인한다.
  - 좀비 워커 펜싱: 임대를 강제로 만료시킨 뒤 두 번째 집기를 하고, 리포트가 1건인지 확인한다.
  - LLM 탐침 DOWN 상태에서 제출하면 시도가 0으로 유지되고, UP이 되면 DONE이 되는지 확인한다.
  - 시도 제한을 2초로 줄인 테스트 설정에서 TIMED_OUT → AUTO_RETRY → ON_HOLD → 재평가 → DONE 흐름을 확인한다.
  - 점수는 `fractions.Fraction`으로 짠 독립 오라클과 무작위 1,000건을 비교한다(반올림 경계 x.xx5 포함).

## 남은 위험과 재검토 조건

- OQ-25~28 팀 결정이 다르면 `state_transitions` 시드와 TRD 03 4절을 함께 바꾼다(마이그레이션 0002).
- 독성 작업 판정(임대 상실 3회부터 시도 소모)의 값은 실측 뒤 조정한다.
- 동시 응시 상한·리포트 3분은 부하 측정(S-6, 8.3) 뒤 확정한다. 넘으면 선평가 동시성과 상한을 다시 본다.
- TRD 03 12절의 변경 제안(EXPIRED 평가 CHECK, `evaluation_runs.manifest_hash`, 제출·리포트 불변 트리거, 설정값 정합)은 아직 반영되지 않았다.
