# ADR-0025: 지원자 수준별 질문 난이도, 코드 품질 검사, 본질문 사전 준비

- 상태: 채택 (2026-11-09)
- 근거: 사용자 지시 2026-11-09 (질문 품질·성능 개선 18개 항목)
- 변경: ADR-0022의 기본값(`question_mode=live`)을 `upfront`로 되돌린다. live 모드는 설정으로 남긴다. QST-02는 PRD 원래 규칙(면접 전 본질문 확정)으로 돌아간다.
- **2026-11-10 철회(기본값만)**: 사용자가 11-07 결정(live)을 다시 확인했다. 기본값은 `live` + 미리 계산이다(ADR-0022 후속). 난이도·품질 검사·시간 로그는 유지한다.

## 배경

실제 면접 기록에서 다음 문제가 보고되었다.

- 신입 지원자에게 Kafka·Redis·Prometheus를 함께 엮은 설계 질문이 나갔다.
- 지원 동기 슬롯이 시스템 아키텍처를 물었다.
- 문장이 길고, 근거에 없는 숫자와 여러 겹의 조건이 붙었다.
- 지원자가 했다고 알려지지 않은 일을 "~하셨을 때"로 가정했다.

live 모드(ADR-0022)에서는 다음 본질문을 면접 중에 만든다. 6 GB GPU에서 llama.cpp `qwen3.5-4b.gguf`(Q4급, `-ngl 99`)의 프롬프트 처리 속도는 약 240 tok/s다. RAG 프롬프트 1,500토큰을 처리하는 데만 약 6 s가 걸리고, 검증 실패로 재시도하면 두 배가 된다. 여기에 임베딩과 즉석 TTS가 더해지면 질문 전환이 10~40 s 걸렸다.

## 결정

1. **지원자 수준** (`app/questions/level.py`, `career_level`)
   - 이력서 경력 기간을 합산한다. 인턴·아르바이트·교육 과정은 제외한다.
   - 1년 미만은 NEW, 1~5년은 JUNIOR, 5년 이상은 SENIOR다.
   - 공고가 "신입"만 요구하면 SENIOR를 JUNIOR로 낮춘다.
2. **난이도 배분** (`difficulty_plan`)
   - 직무·프로젝트 슬롯에 기초 : 실무 적용 : 심화를 배분한다. NEW 50:40:10, JUNIOR 30:50:20, SENIOR 10:50:40이다.
   - 최대 잉여 방식으로 나누고, 쉬운 것부터 앞 순번에 배치한다.
   - 꼬리질문 난이도는 답변에 맞춘다. 구체적인 답변에는 한 단계 깊게, 모호한 답변에는 같은 수준 이하로 묻는다(T4 프롬프트).
3. **프롬프트 순서**
   - T2·T3 프롬프트 맨 앞에 지원자 수준과 슬롯별 난이도를 둔다.
   - 회사 자료(RAG)는 질문을 구체적으로 만드는 데만 쓴다.
   - 신입의 직무 질문에는 "회사 자료에서만 근거" 강제를 적용하지 않는다(공고 문장 허용).
4. **코드 품질 검사** (`problems`, 모델 호출 없음). T2·T3·T4 검사에서 다음을 거부한다.
   - 기술 3개 이상, 또는 신입에게 기술 2개 이상인 심화 질문 (MANY_TOPICS)
   - 수준별 길이 초과(80/90/100자) 또는 쉼표 3개 이상 (TOO_LONG)
   - 근거에 없는 숫자 (NUMBER)
   - 동기 슬롯의 설계·다기술 질문 (NOT_MOTIVATION)
   - 직무 슬롯의 지원 동기 질문 (NOT_JOB)
   - 근거 없는 경험 가정 (PRESUMES_EXPERIENCE)
   - 배분보다 많은 심화 질문 (TOO_HARD)

   거부 사유는 재생성 피드백에 그대로 넣는다. 그래서 재시도 1회로 고쳐질 가능성이 높아지고, 추가 "검증용 LLM 호출"은 두지 않는다. 생성된 질문의 `grounding`에는 `level`과 `difficulty`를 기록한다.
5. **질문은행 대체**: 같은 유형 안에서 수준에 맞는 질문(`fits_level`)을 먼저 고른다.
6. **본질문 사전 준비** (`question_mode=upfront` 기본)
   - 면접 시작 전 `compose_questions` 그래프가 본질문 전부를 생성·검증·저장한다.
   - `tts_pregen`이 모든 본질문 음성을 미리 만든다.
   - 면접 중 실시간 LLM 호출은 꼬리질문(T4)뿐이다.
   - 무응답·시간 초과는 T4 전에 규칙으로 건너뛰어(SKIP RULE) 준비된 다음 질문으로 바로 간다.
7. **단계별 시간 로그** (텍스트 없음, 시간만)

   | 로그 | 측정 대상 |
   |---|---|
   | `compose_stage` | 노드별 시간, total |
   | `rag_stage` | retrieve, generate |
   | `llm_task` | latency, queue, tokens |
   | `tts_pregen_one` / `tts_pregen_done` | 사전 TTS |
   | `tts_live` / `tts_not_pregenerated` | 즉석 TTS |
   | `question_transition` | 답변 확정 → 다음 질문 표시 (duration_ms), 그중 음성 준비 시간 (latency_ms) |

## 결과와 trade-off

- 다음 본질문이 직전 답변을 반영하지 못한다(ADR-0022의 장점). 답변 연결은 꼬리질문이 맡는다.
- 질문 준비 시간이 면접 전(PREPARING)으로 옮겨 간다. 지원자는 준비 완료까지 기다린다. 기존 화면의 준비 상태 표시를 쓴다.
- 코드 검사는 규칙 기반이어서 오탐·누락이 있을 수 있다. 오탐은 질문은행 대체로 끝나며, 면접을 막지 않는다.
- 모델·벡터DB는 바꾸지 않았다(교체 근거 없음).

## 측정 (2026-11-09, 실제 모델, GTX 1660 SUPER 6 GB)

조건:
- 별도 DB `aihire_qe2e`를 쓴다. 가상 회사 3곳, 신입 공고 3개, 신입 이력서 3개(인턴만 있음, 경력 없음, 교육생만 있음).
- 텍스트 모드로 API 전 과정을 진행하고, 지원자당 10문항, 꼬리질문 최대 2개다.
- 음성 브라우저 E2E와 외부망 WebRTC는 실행하지 않았다.

| 항목 | 이전 (live) | 이후 (upfront) |
|---|---|---|
| 질문 준비 (prepare→준비 완료) p50 / p95 | 2.4 / 2.6 s (첫 질문만) | 91.7 / 95.1 s (본질문 10개 + TTS 10개) |
| 다음 본질문 전환 p50 / p95 (n=27) | 11.0 / 25.4 s | **0.16** / 6.8 s |
| 꼬리질문 전환 p50 / p95 (n=6) | 3.9 / 6.7 s | 3.8 / 4.0 s |
| 실제 면접 로그 (사용자 세션, live) | 답변 확정→다음 질문 6~38 s (중앙값 10 s) | — |
| 꼬리질문 즉석 TTS | 2.1~3.1 s | 1.7~3.7 s |

- LLM 호출이 필요 없는 전환(무응답·꼬리질문 없음)은 0.16~0.34 s다.
- 이후 p95 6.8 s는 내용 있는 답변에 대한 꼬리질문 판단(T4, LLM 1회)이 "묻지 않음"으로 끝난 경우다.
- 준비 단계 노드별 시간(1회 예):

  | 노드 | 시간 |
  |---|---|
  | personality | 4.8 s |
  | collaboration | 4.5 s |
  | project | 23.7 s |
  | motivation | 14.9 s |
  | job_skill | 5.3 s |
  | adapt | 12.0 s |
  | 합계 | 65 s |

  TTS 10개는 별도 작업이다.

품질(이후, 모델 생성 질문 22개):
- 3개 이상 기술을 엮은 질문, 근거 없는 숫자, 설계·아키텍처를 묻는 동기 질문은 0개였다.
- 이력서 질문 꼬리말은 한 가지만 묻도록 바꿨다(역할 / 선택 이유 / 다시 한다면).
- 남은 점: 이력서 문장을 그대로 되짚는 앞부분 때문에 이력서 질문 2개가 80자를 넘었다(87·94자). 질문은행 대체 질문 일부("~맞춘 방법을 말씀해 주세요")는 경험을 전제한다.

## 확장 지점

- 난이도 비율은 `MIX` 상수다. 공고 설정으로 옮길 수 있다.
- 질문은행에 난이도 열이 없다. 지금은 문장 복잡도로 추정한다.
