# ADR-0003: 단일 LLM 공유 — 게이트웨이 우선순위 레인과 선점
- 상태: 채택(임시) — 판단 마감과 8.2 5초의 관계는 OQ-31, 모델 선정은 X-11(ADR-0004)
- 날짜: 2026-10-27
- 작성: 에이전트 C / 통합 F
- 관련: 8.1, 8.2, 8.3, QST-05, 6.2, EVL-05·06, INT-14, OQ-23, OQ-31, consolidation-round1 T3·T4·T15·T16·T27

## 맥락

- 8.1은 4bit LLM 하나를 질문 생성·꼬리질문·평가에 함께 쓰라고 정했다. 꼬리질문은 답변 종료 뒤 5초 안에 정하지 못하면 건너뛴다(6.2). 평가는 시도당 10분, 리포트는 3분 목표다(8.2).
- Ollama에는 요청 우선순위가 없다. 현재 장비에서 병렬 처리는 1이다: 600토큰 생성 뒤에 짧은 요청이 11.06초 기다렸다[실측].
- Ollama 서버 설정(`OLLAMA_NUM_PARALLEL` 등)은 사용자 장비의 서비스 설정이라 바꾸지 않는다.

## 결정

1. 모든 LLM 호출은 `ai` 프로세스의 게이트웨이 하나를 거친다. `app`·`worker`는 Ollama를 직접 부르지 않는다.
2. 레인 3개, 엄격 우선순위: **RT**(꼬리질문 판단) > **INTERACTIVE**(이력서 추출, 질문 생성) > **BATCH**(문항 평가, 종합 리포트, 지원자 피드백, 코드 리뷰). Ollama로는 동시에 1개만 보낸다.
3. 선점: 상위 레인 요청이 오면 진행 중인 하위 레인 스트림 연결을 끊고 그 요청을 대기열 앞에 다시 넣는다. 응답 코드 `PREEMPTED`. **시도 횟수·형식 재요청 횟수를 소모하지 않는다.**
4. 마감: 요청마다 절대 마감 `deadline_ms`. 대기 + 예상 실행이 넘으면 즉시 `DEADLINE_EXCEEDED`, 실행 중 마감에 닿으면 스트림을 끊는다. 꼬리질문 마감은 답변 종료 + **5.0초(PRD 값 유지, T27)**.
5. 요청 인자 고정: `stream=true`(취소 가능), `num_ctx=8192` 전역(T4), `keep_alive=-1`, `think=false`, `format`=JSON Schema.
6. LLM 불가(최근 15초 탐침 실패, 연결 거부, 5xx, 모델 미적재)면 `LLM_UNAVAILABLE`. worker는 이 상태에서 LLM 작업을 집지 않고 실행 중이면 임대를 반납한다(시도 미소모, OQ-23·AC-18, ADR-0006).
7. worker의 LLM 작업 동시성은 레인당 1(INTERACTIVE 1, BATCH 1). 실제 GPU 순서는 게이트웨이가 호출 단위로 정한다.
8. 평가는 답변 단위 호출로 쪼갠다(선점 손실을 1단위로 제한, EVL-05 선평가와 결합, T15).

## 검토한 대안 (장단점)

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| A. 병렬 1 + 게이트웨이 선점 | 서버 설정 불변, 취소가 실제 동작[실측], VRAM 추가 없음 | 선점된 BATCH 생성 시간 낭비 | **채택** |
| B. `NUM_PARALLEL=2` + RT 예약 슬롯(C 1단계안) | RT가 거의 기다리지 않음, RT 프롬프트 캐시 유지 가능 | 사용자 장비 서비스 설정 변경, KV 슬롯 2배로 STT GPU 여유 감소, 병렬 시 요청당 속도 저하 미측정 | 기각(C가 리뷰에서 철회). S-11 미달 시 사용자 승인을 받아 재검토 |
| C. Ollama FIFO에 맡김 | 구현 없음 | 평가 뒤에서 꼬리질문이 11초 대기 → 6.2 건너뜀 상시 발생 | 기각 |
| D. 실시간용 4B + 평가용 8B 두 모델 | 평가 품질 상한 | 8.1 "LLM 하나" 위반, VRAM 부족 | 기각 |

## 근거

- [실측] 스트림 연결 종료 직후 짧은 요청 0.49초 처리, 미취소 시 11.06초 대기(`results-ollama-scheduling.txt`).
- [실측] `num_ctx`가 요청마다 다르면 약 5.1초 재적재, 4096→8192에서 VRAM 2,995→3,209 MiB.
- [실측] 콜드 로드 약 40초 → `keep_alive=-1` 필요(프로토타입의 `"30m"`은 유휴 뒤 언로드).
- [실측] 꼬리질문 판단 웜 0.56~0.57초, 문항 평가 6~11초. 단 판단 값은 같은 프롬프트 반복 측정이고 새 프롬프트 첫 호출 prefill은 205~232 tok/s였다.

## 결과와 영향

- `ai` 내부 API `POST /v1/llm/{task}`와 응답 코드(409 `PREEMPTED`, 504 `DEADLINE_EXCEEDED`, 503 `LLM_UNAVAILABLE`, 422 `OUTPUT_INVALID`). 계약은 TRD 05 §4·§5.
- B의 작업 큐는 작업 종류→레인 매핑을 갖고 레인별 세마포어로 집는다. 선점 대기 누계는 사용량 기록에만 쓰고 EVL-06 10분 계산은 그대로 둔다(임대 시작부터).
- 게이트웨이 로그는 작업명·토큰 수·지연·버전·오류 코드만(SEC-08).

## 남은 위험과 재검토 조건

- 실제 조건(서로 다른 답변, BATCH 동시)의 꼬리질문 p95가 미측정(S-11). p95 > 2.5초 또는 건너뜀 > 10%면 프롬프트 축소 → Qwen3-4B-Instruct-2507 비교 → 대안 B(사용자 승인) 순으로 재검토. 8.2 5초를 넘으면 팀에 판단 마감 단축 제안(OQ-31).
- STT가 같은 GPU를 쓴다. 생성 중 STT 지연(S-10)이 기준을 넘으면 `gpu_policy=stt_preempts_batch`(STT 요청이 BATCH 스트림을 선점)를 켠다(ADR-0004).
- `ai`는 단일 장애점이다. 장애 시 면접은 꼬리질문 건너뜀으로 계속, 평가는 복구 후 진행(8.3).
