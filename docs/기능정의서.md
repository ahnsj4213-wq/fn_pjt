## 1. 개요

### 1.1 목적
구직자가 직무와 난이도를 골라 AI 면접관과 모의면접을 진행하고, 루브릭 기반 피드백 리포트를 받는 웹 서비스를 만든다. 관리자는 회원, 질문 데이터, 면접 결과를 관리한다.

### 1.2 핵심 흐름
```
AI가 음성(TTS)으로 질문 → 구직자가 실시간 음성(WebRTC)으로 답변 → (필요 시) 꼬리질문 → 다음 질문 … → 면접 종료 → 루브릭 기반 피드백 리포트
```

### 1.3 사용자 역할
| 역할 | 설명 | 계정 생성 방법 |
|---|---|---|
| 구직자 (candidate) | 모의면접을 보고 본인 리포트를 확인한다 | 회원가입 화면에서 직접 가입 |
| 관리자 (admin) | 회원·질문·면접 결과를 관리한다 | 초기 시드 스크립트로 생성 (회원가입 화면으로는 만들 수 없음) |

### 1.4 범위
| 구분 | 내용 |
|---|---|
| 포함 | 회원관리(구직자/관리자), 질문 데이터 적재와 임베딩, 벡터 검색 기반 질문 선택, LLM 꼬리질문, WebRTC 실시간 음성 답변(VAD → STT, 실시간 자막), AI 음성 질문(TTS), 텍스트 답변(대체 수단), 루브릭 기반 리포트, 관리자 화면 |
| 제외 | 영상 송수신, 표정·음성 감정 분석, 코딩 IDE, 화이트보드, 클라우드 배포, Kubernetes, 유료 API |

### 1.5 실행 환경 (학원 PC 기준)
| 항목 | 사양 |
|---|---|
| GPU | NVIDIA GTX 1660 Super (VRAM 6GB) |
| RAM | 64GB |
| 배포 | 로컬 실행. PostgreSQL은 Docker, 백엔드(FastAPI, 8000번 포트)·프론트엔드(Next.js, 3000번 포트)는 로컬 프로세스로 실행 (GPU 연동을 단순하게 하기 위함) |
| 네트워크 | 브라우저와 서버를 같은 PC에서 실행(localhost). 다른 PC에서 접속하면 브라우저가 마이크를 쓰도록 HTTPS가 필요 |

## 2. 기술 스택

| 구분 | 기술 | 비고 |
|---|---|---|
| 프론트엔드 | Next.js (App Router), TypeScript | 화면만 담당. 데이터 요청은 모두 FastAPI로 보내고, Next.js의 Route Handler·Server Action으로 DB나 모델에 접근하지 않음. `/api/*` 요청은 `next.config.ts`의 rewrites로 FastAPI에 넘김. 마이크·WebRTC·토큰을 쓰는 화면은 클라이언트 컴포넌트(`'use client'`). 마이크는 getUserMedia(에코 제거·잡음 억제 켬), 음성 송수신은 브라우저 WebRTC API |
| 백엔드 | FastAPI (Python 3.11), SQLAlchemy, Pydantic | 리포트 생성은 FastAPI BackgroundTasks로 비동기 처리 |
| DB | PostgreSQL 16 | Docker 이미지 `pgvector/pgvector:pg16` |
| 벡터 DB | pgvector | 질문 임베딩 저장, 코사인 유사도 검색 |
| 인증 | JWT (Access Token), bcrypt | |
| 실시간 통신 | aiortc (Python WebRTC) | FastAPI 프로세스 안에서 실행. 시그널링은 HTTP offer/answer 1회, 상태·자막 이벤트는 DataChannel |
| LLM | `Qwen2.5-7B-Instruct` GGUF Q4_K_M (약 4.7GB) + llama-cpp-python | GPU 실행. 느리면 `EXAONE-3.5-2.4B-Instruct` GGUF로 교체. 1660 Super는 FP16 연산이 불안정해 transformers 대신 GGUF 사용 |
| VAD | `silero-vad`, CPU | 16kHz, 512샘플(32ms) 단위로 발화 감지 |
| STT | `faster-whisper` small (필요 시 medium), int8, CPU | 언어 `ko` 고정. VAD가 자른 발화 구간 단위로 변환 |
| TTS | MeloTTS 한국어 (`myshell-ai/MeloTTS-Korean`), CPU | 22.05kHz 출력. 본질문 음성은 파일로 캐시 |
| 임베딩 | `BAAI/bge-m3` (1024차원), CPU | sentence-transformers |
| 질문 데이터 | AI Hub 「채용면접 인터뷰 데이터」, Hugging Face 면접 질문 데이터셋 | 사용 전 데이터 라이선스 확인 |

> 모든 모델은 Hugging Face에서 직접 내려받아 로컬에서 추론한다. VRAM 6GB는 LLM 전용으로 쓰고, VAD·STT·TTS·임베딩은 CPU에서 실행한다.

### 2.1 실시간 음성 파이프라인

면접 한 턴은 서버의 세 상태를 돈다. 상태가 바뀔 때마다 DataChannel로 브라우저에 알린다.

| 상태 | 서버가 하는 일 | 화면 |
| --- | --- | --- |
| `ai_speaking` | 질문을 TTS로 합성해 WebRTC 오디오 트랙으로 송출. 이 동안 마이크 입력은 무시 (반이중) | 면접관 말하는 중, 질문 자막 |
| `listening` | 받은 음성을 16kHz로 바꿔 VAD로 발화 감지, 0.6초 쉬면 그 구간을 바로 STT, 자막 전송 | 듣는 중, 실시간 자막, [답변 완료] |
| `thinking` | 마지막 구간 STT, 답변 저장, 꼬리질문 판단(LLM) 또는 다음 본질문 검색 | 맞장구 음성 후 생각 중 표시 |

답변 종료가 확정된 뒤(2.5초 침묵 또는 [답변 완료]) 다음 질문 음성이 나오기까지의 목표 시간이다.

| 단계 | 목표 |
| --- | --- |
| 맞장구 음성 재생 (미리 만든 파일) | 1초 이내 |
| 마지막 구간 STT (CPU) | 1초 |
| 꼬리질문 판단·생성 (LLM, GPU) | 3초 |
| 질문 TTS 첫 음성 (CPU) | 0.7초 |
| 합계 | 꼬리질문 5초, 다음 본질문 2초 이내 (LLM 없이 벡터 검색과 캐시된 TTS) |

원본 계획서의 1.5초 목표는 GTX 1660 Super에서 7B LLM으로는 어려워 5초로 잡았다. 측정해서 LLM이 느리면 `Qwen2.5-3B-Instruct`로 바꾸고 남는 VRAM으로 STT를 GPU에 올린다.

## 4. 기능 상세

### AUTH-01 회원가입
| 항목 | 내용 |
|---|---|
| 입력 | 이메일, 비밀번호, 비밀번호 확인, 이름 |
| 검증 | 이메일 형식, 이메일 중복 불가, 비밀번호 8자 이상(영문+숫자 포함), 비밀번호 확인 일치, 이름 1~20자 |
| 처리 | 비밀번호를 bcrypt로 해시해 `role=candidate`로 저장 |
| 출력 | 가입 완료 후 로그인 화면으로 이동 |
| 예외 | 중복 이메일 → "이미 가입된 이메일입니다." |

### AUTH-02 로그인
| 항목 | 내용 |
|---|---|
| 입력 | 이메일, 비밀번호 |
| 처리 | 비밀번호 검증 후 JWT Access Token 발급 (유효시간 60분, payload: user_id, role) |
| 출력 | 구직자 → 구직자 홈, 관리자 → 관리자 대시보드 |
| 예외 | 불일치 → "이메일 또는 비밀번호가 올바르지 않습니다." / 비활성 계정 → "이용이 제한된 계정입니다." / 토큰 만료 → 로그인 화면으로 이동 |

### AUTH-06 회원 탈퇴
| 항목 | 내용 |
|---|---|
| 입력 | 현재 비밀번호, 탈퇴 확인 체크 |
| 처리 | 사용자, 면접, 턴, 리포트를 CASCADE 삭제하고 서버의 녹음 파일 폴더도 삭제 |
| 출력 | 로그아웃 후 로그인 화면으로 이동 |

### QST-01 질문 데이터 적재
| 항목 | 내용 |
|---|---|
| 입력 | AI Hub/HF 원본 파일 (JSON/CSV) |
| 처리 | ① 질문 문장 추출 ② 직무·유형(기술/인성)·난이도 매핑 ③ 공백·중복 제거 (정규화한 문장 기준) ④ DB 저장 ⑤ QST-02 호출 |
| 출력 | 적재 건수, 중복 제외 건수, 실패 건수 로그 |
| 비고 | 난이도 정보가 없는 데이터는 기본값 `2(보통)`로 저장하고 관리자가 수정 |

### QST-02 질문 임베딩 생성
| 항목 | 내용 |
|---|---|
| 처리 | 질문 본문을 bge-m3로 임베딩 (정규화된 1024차원 벡터) 후 `questions.embedding`에 저장 |
| 시점 | 적재 시 일괄 생성, 관리자가 질문을 등록·수정할 때 해당 건만 재생성 |
| 인덱스 | `embedding`에 HNSW 인덱스 (`vector_cosine_ops`) |

### QST-05 유사 질문 검색
| 항목 | 내용 |
|---|---|
| 입력 | 검색 문장, 개수 N (기본 10), 선택 필터(직무, 유형, 난이도) |
| 처리 | 검색 문장을 임베딩해 코사인 거리 순으로 상위 N개 조회 |
| 출력 | 질문 목록과 유사도 점수 |
| 용도 | 관리자의 중복 질문 확인, 벡터 검색 동작 검증 |

### INT-01 면접 설정
| 항목 | 입력값 |
|---|---|
| 직무 | 질문 데이터에 있는 직무 목록에서 선택 (예: 백엔드 개발, 프론트엔드 개발, 데이터 분석 등) |
| 난이도 | 쉬움(1) / 보통(2) / 어려움(3) |
| 본질문 수 | 3~10개, 기본 5개 |
| 질문 유형 | 기술 / 인성 / 혼합 (기본 혼합) |

### INT-02 면접 시작
| 항목 | 내용 |
|---|---|
| 처리 | ① `interviews` 레코드 생성 (`status=in_progress`) ② 첫 질문 선택: 설정 조건에 맞는 질문 중 무작위 1개 (첫 질문은 직전 답변이 없으므로 벡터 검색을 쓰지 않음) ③ 턴 저장 ④ 면접 화면에서 WebRTC 연결(INT-11) 후 첫 질문을 음성으로 송출 |
| 출력 | 면접 진행 화면으로 이동, 첫 질문 표시 |
| 예외 | 조건에 맞는 질문이 본질문 수보다 적으면 → "선택한 조건의 질문이 부족합니다. 조건을 바꿔주세요." / 진행 중(`in_progress`)인 면접이 있으면 확인 후 이전 면접을 `aborted`로 바꾸고 새로 시작 (구직자당 진행 중 면접은 1개) |

### INT-04 텍스트 답변
| 항목 | 내용 |
|---|---|
| 입력 | 답변 텍스트 (1~2,000자) |
| 처리 | 턴에 답변 저장 (`answer_type=text`) → 본질문이면 INT-07, 꼬리질문이면 INT-06 실행 |
| 출력 | 다음 질문(꼬리질문 또는 다음 본질문) 또는 면접 종료 |
| 예외 | 빈 답변 제출 불가. "잘 모르겠습니다" 같은 짧은 답변은 허용 |

### INT-05 실시간 음성 답변
| 항목 | 내용 |
| --- | --- |
| 입력 | WebRTC 오디오 트랙 (Opus, 48kHz) |
| 처리 | ① 받은 음성을 16kHz 모노로 변환 ② silero-vad로 32ms 단위 발화 감지 ③ 0.6초 이상 쉬면 그 구간을 faster-whisper로 바로 변환 ④ 변환된 문장을 DataChannel `partial`로 보내 자막에 이어 붙임 ⑤ 답변 종료가 확정되면 남은 구간을 변환하고 답변 전체를 저장 (`answer_type=voice`, wav 파일, 길이) |
| 답변 종료 | 발화 후 2.5초 침묵, [답변 완료] 버튼, 최대 3분 중 먼저 오는 것 |
| 출력 | 본질문이면 INT-07, 꼬리질문이면 INT-06으로 이동 |
| 예외 | 마이크 권한 거부·연결 실패 → 텍스트 답변(INT-04)으로 전환 / 15초 동안 말이 없으면 "편하게 답변을 시작해주세요" 자막 / 인식 결과가 비면 "잘 들리지 않았어요. 다시 말씀해주세요."를 음성으로 안내하고 다시 듣기 |
| 비고 | AI가 말하는 동안 들어온 음성은 무시한다. 스피커 소리가 마이크로 다시 들어가지 않도록 브라우저 에코 제거를 켜고 이어폰 사용을 권장 |

### INT-11 음성 연결 (WebRTC)
| 항목 | 내용 |
| --- | --- |
| 시점 | 면접 진행 화면 진입 시 (새로고침·재접속 포함) |
| 처리 | ① 브라우저가 마이크 트랙과 DataChannel `events`를 담은 offer 생성 ② `POST /interviews/{id}/rtc/offer`로 전송 ③ 서버(aiortc)가 answer를 돌려주고, 마이크 트랙을 음성 파이프라인에 연결, TTS용 오디오 트랙 추가 ④ 연결되면 현재 질문을 음성으로 송출 |
| 네트워크 | 같은 PC(localhost)에서 접속하므로 STUN/TURN 서버 없이 host 후보만 사용 |
| 연결 관리 | 면접 1개당 연결 1개. 새 연결이 오면 이전 연결을 닫음. 끊기면(`failed`/`closed`) 서버가 자원을 정리하고 면접은 `in_progress` 유지. 브라우저는 1회 자동 재연결 |
| 예외 | 10초 안에 연결되지 않으면 "음성 연결에 실패했어요. 텍스트로 진행할까요?" → 텍스트 모드 |

### INT-12 질문 음성 생성 (TTS)
| 항목 | 내용 |
| --- | --- |
| 처리 | 질문 문장을 MeloTTS(KR)로 합성 → PCM을 오디오 프레임으로 잘라 실시간 속도로 송출. 같은 문장을 DataChannel `question`으로 보내 자막 표시 |
| 캐시 | 본질문 음성은 `storage/tts/{question_id}.wav`에 저장해 재사용. 꼬리질문은 매번 생성 |
| 맞장구 음성 | 답변이 끝나면 미리 만든 짧은 음성("네, 잘 들었습니다." 등 3종 중 하나)을 바로 재생해 LLM이 생각하는 시간을 메움 |
| 상태 알림 | 송출 시작 시 `state=ai_speaking`, 끝나면 `state=listening` |

### INT-06 다음 질문 선택 (벡터 검색 + MMR)
| 항목 | 내용 |
|---|---|
| 시점 | 본질문의 답변(꼬리질문이 있었다면 꼬리질문의 답변까지) 처리 후 |
| 쿼리 | `직전 본질문 + 직전 답변` 문장을 bge-m3로 임베딩 |
| 후보 검색 | 설정 조건(직무, 난이도, 유형) 필터 + 이번 면접에서 이미 나온 질문 제외 → 코사인 유사도 상위 20개 |
| MMR 선택 | `score = λ × 쿼리와의 유사도 − (1 − λ) × 이미 나온 질문들과의 최대 유사도`, λ = 0.5. 가장 높은 1개 선택 |
| 의도 | 직전 답변과 이어지는 주제를 고르되, 이미 물어본 질문과 비슷한 질문은 피한다 |
| 유형 혼합 | 유형이 '혼합'이면 기술/인성을 번갈아 필터링 |
| 종료 조건 | 본질문 수에 도달하면 INT-08로 이동 |

### INT-07 꼬리질문 생성
| 항목 | 내용 |
|---|---|
| 시점 | 본질문에 답변한 직후. 본질문 1개당 꼬리질문 최대 1개 |
| 입력 | 직무, 본질문, 답변 |
| 처리 | LLM에 아래 JSON 스키마로 출력을 강제 (llama.cpp JSON 스키마 제약) |
| 판단 기준 | 답변이 구체적인 경험·기술을 언급해 더 깊게 물을 수 있으면 생성. 답변이 비어 있거나 "모르겠다"이면 생성하지 않음 |
| 실패 처리 | JSON 파싱 실패 시 최대 2회 재시도, 그래도 실패하면 꼬리질문 없이 INT-06 진행 |

```json
{
  "need_followup": true,
  "followup_question": "MSA 도입 시 서비스 간 트랜잭션은 어떻게 관리하셨나요?",
  "reason": "MSA 경험을 언급했지만 구체적인 문제 해결 과정이 없음"
}
```

시스템 프롬프트 요지:
> 당신은 {직무} 분야의 시니어 면접관입니다. 지원자의 답변을 읽고, 답변에서 언급한 경험이나 개념을 더 깊이 확인할 수 있는 꼬리질문이 필요한지 판단하세요. 꼬리질문은 한 문장, 정중한 존댓말로 작성하고 정답을 알려주지 마세요.

### INT-08 면접 종료
| 구분 | 처리 |
|---|---|
| 정상 종료 | 마지막 본질문(과 꼬리질문)에 답하면 `status=completed`, `ended_at` 저장 → RPT-01 시작 → 리포트 화면으로 이동 |
| 중단 | 사용자가 [면접 중단] 클릭 → 확인 창 → `status=aborted`. 리포트를 만들지 않음 |
| 이탈 | 진행 중 브라우저를 닫거나 음성 연결이 끊기면 `in_progress`로 남음. 면접 이력에서 [이어하기]로 다시 연결해 마지막 미답변 질문을 음성으로 다시 들려주고 재개 |

### RPT-01 리포트 생성
| 항목 | 내용 |
|---|---|
| 시점 | 면접 정상 종료 직후 백그라운드 실행 |
| 상태 | `pending` → `generating` → `done` / `failed` |
| 1단계: 문항별 평가 | 본질문 1개와 그 꼬리질문을 한 묶음으로 LLM에 전달해 루브릭 점수와 피드백 생성 (5장 루브릭 사용) |
| 2단계: 종합 평가 | 문항별 결과를 모아 종합 요약, 강점 3개, 개선점 3개 생성 |
| 점수 계산 | 항목별 점수 = 문항 점수 평균 (소수점 1자리). 종합 점수 = 세 항목 평균 × 20 (100점 환산) |
| 실패 처리 | 문항 단위로 2회 재시도. 그래도 실패하면 `failed`와 오류 메시지 저장 → RPT-03으로 재생성 |
| 화면 반영 | 리포트 화면이 3초마다 상태를 조회해 완료되면 결과 표시 |

### RPT-02 리포트 조회
| 구성 | 내용 |
|---|---|
| 종합 | 종합 점수(100점), 항목별 점수(5점), 종합 요약, 강점, 개선점 |
| 문항별 | 질문, 내 답변(음성이면 녹음 재생), 꼬리질문과 답변, 항목별 점수, 피드백, 모범 답변 예시 |
| 권한 | 구직자는 본인 리포트만, 관리자는 전체 조회 |

## 5. 평가 루브릭

원본 계획서 8.1절의 루브릭을 사용한다. 각 항목은 1~5점이며, 2점과 4점은 인접 기준의 중간이다.

| 평가 항목 | 1점 (미흡) | 3점 (보통) | 5점 (탁월) |
|---|---|---|---|
| 개념 이해도 | 핵심 개념을 정의하지 못하거나 오개념을 가지고 있음 | 개념은 정확히 정의하나 실무 적용 사례를 제시하지 못함 | 개념을 정확히 이해하고 장단점(Trade-off)과 실제 적용 사례를 논리적으로 설명함 |
| 문제 해결력 | 문제 해결의 실마리를 찾지 못함 | 문제를 해결하나 최적화된 방법은 아님 | 문제를 스스로 정의하고 여러 해결책을 비교해 최적해를 도출함 |
| 커뮤니케이션 | 답변이 장황하고 핵심이 불분명함 | 질문 의도를 파악해 대답하나 구조화가 부족함 | 두괄식으로 명확히 답변하고 논리적으로 구조화됨 |

> 인성 질문의 '개념 이해도'는 "질문 의도와 자기 경험의 연결", '문제 해결력'은 "STAR(상황·과제·행동·결과) 구조로 경험을 설명했는지"로 해석해 평가하도록 프롬프트에 명시한다.
> 원본 루브릭의 비언어적 태도·시선 처리 기준은 영상 분석을 제외했으므로 쓰지 않는다.

### 5.1 문항별 평가 출력 스키마
```json
{
  "concept_score": 4,
  "problem_solving_score": 3,
  "communication_score": 4,
  "feedback": "트랜잭션 관리 경험은 구체적이지만 Saga 패턴을 선택한 이유가 빠졌습니다.",
  "model_answer": "저는 주문·결제 서비스를 분리하면서 Saga 패턴을 도입했습니다. ..."
}
```

### 5.2 종합 평가 출력 스키마
```json
{
  "summary": "기술 개념은 정확하지만 경험을 구조화해 설명하는 연습이 필요합니다.",
  "strengths": ["...", "...", "..."],
  "improvements": ["...", "...", "..."]
}
```

### 7.1 답변 제출 응답 예시 (`POST /interviews/{id}/answers`)
```json
{
  "finished": false,
  "next_turn": {
    "turn_id": 12,
    "seq": 4,
    "is_followup": true,
    "question_text": "그때 트랜잭션은 어떻게 관리하셨나요?"
  },
  "progress": { "main_done": 2, "main_total": 5 }
}
```
마지막 답변이면 `"finished": true, "next_turn": null`을 반환하고 리포트 생성을 시작한다.

### 7.2 DataChannel 메시지

음성 모드에서 상태와 자막은 DataChannel `events`로 주고받는다. 모든 메시지는 `{"type": ..., ...}` 형식의 JSON이다.

| 방향 | type | 내용 |
| --- | --- | --- |
| 서버 → 브라우저 | `state` | `ai_speaking` / `listening` / `thinking` |
| 서버 → 브라우저 | `question` | turn_id, text, is_followup, progress |
| 서버 → 브라우저 | `partial` | 지금까지 인식된 답변 문장 |
| 서버 → 브라우저 | `answer_saved` | turn_id, 최종 답변 텍스트 |
| 서버 → 브라우저 | `finished` | 면접 종료, 리포트 생성 시작 |
| 서버 → 브라우저 | `error` | message |
| 브라우저 → 서버 | `answer_done` | [답변 완료] 버튼 |
| 브라우저 → 서버 | `switch_text` | 텍스트 모드로 전환 |

## 8. 비기능 요구사항

| 구분 | 요구사항 | 목표 (학원 PC 기준, 구현 후 측정해 조정) |
|---|---|---|
| 응답 시간 | 답변 종료 확정 후 다음 질문 음성 시작 | 꼬리질문 5초, 다음 본질문 2초 이내 (2.1절). 맞장구 음성은 1초 이내 |
| 응답 시간 | 말하는 동안 자막 | 발화 구간이 끝난 뒤 2초 이내 |
| 음성 품질 | 에코·잡음 | getUserMedia의 echoCancellation·noiseSuppression 켬, AI 발화 중 입력 무시, 이어폰 권장 |
| 응답 시간 | 본질문 5개 리포트 생성 | 3분 이내 |
| 동시성 | 동시 면접 세션 | 1개 (실시간 음성이 CPU의 STT·TTS와 GPU의 LLM을 함께 씀). LLM 호출은 전역 잠금으로 한 번에 하나씩 처리 |
| 보안 | 비밀번호 | bcrypt 해시 저장, 평문 저장·로그 출력 금지 |
| 보안 | 권한 | 모든 API에서 역할과 본인 여부 검사. 다른 사람의 면접·녹음 접근 시 403 |
| 보안 | 입력 검증 | Pydantic으로 요청 검증, 음성 답변은 최대 3분에서 자름 |
| 개인정보 | 데이터 삭제 | 회원 탈퇴 시 DB 데이터와 녹음 파일 즉시 삭제 |
| 품질 | LLM 출력 | 모든 LLM 출력은 JSON 스키마 제약으로 생성하고 서버에서 다시 검증 |
| 운영 | 실행 | `README`의 순서대로 DB 컨테이너 실행 → 모델 다운로드 → 시드·적재 스크립트 → 서버 실행 |
| 운영 | 로그 | LLM 호출별 소요 시간과 토큰 수를 로그로 남겨 성능 측정에 사용 |

## 9. 일정 (3주)

| 주차 | 작업 | 관련 기능 | 완료 기준 |
|---|---|---|---|
| 1주차 전반 | 프로젝트 구조, DB, 회원관리, 질문 적재·임베딩, WebRTC 음성 왕복 PoC | AUTH-*, QST-01~02, QST-05, INT-11 | 두 역할로 로그인, 유사 질문 검색 동작, 브라우저 음성이 서버를 거쳐 다시 들림 |
| 1주차 후반~2주차 중반 | 면접 엔진 (텍스트 모드 → 실시간 음성: VAD, STT, TTS) | INT-01~09, INT-12 | 음성만으로 본질문 5개와 꼬리질문까지 한 세션을 끝내고 턴이 저장됨 |
| 2주차 후반 | 리포트 생성·조회 | RPT-01~03 | 면접 완료 후 스키마 검증을 통과한 리포트가 저장되고 화면에 표시됨 |
| 3주차 | 관리자 기능, 화면 다듬기, 지연 시간 측정·튜닝, README와 시연 영상 | ADM-*, QST-03~04, INT-10, INT-13 | 가입부터 리포트 열람, 관리자 조회까지 처음부터 끝까지 시연됨 |

WebRTC 음성 왕복이 1주차 안에 동작하지 않으면 녹음 후 업로드 방식으로 면접 흐름을 먼저 완성하고, WebRTC는 그 위에 이어 붙인다.
