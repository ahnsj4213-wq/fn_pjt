1. 이 프로그램은 뭘 하나요?

회사에 지원하는 사람이 AI 면접관과 말로 모의면접을 하면, 프로그램이 점수와 피드백이 담긴 리포트를 만들어 줍니다. 기업 담당자는 그 리포트를 보고 합격·보류·불합격을 직접 정합니다. 모든 AI는 회사 안의 컴퓨터에서만 돌고, 외부 AI 서비스로 데이터를 보내지 않습니다.

왜AI가 합격을 정하지 않는 이유. CLAUDE.md §1이 "AI는 합격·불합격을 결정하거나 추천하지 않는다"를 프로젝트 원칙으로 못 박았습니다(이유 설명은 거기에 따로 없고, 사람의 일자리가 걸린 결정이라 사람이 책임지게 한 것으로 이해하면 됩니다 — 이 문장은 제 해석입니다). AI는 "점수와 근거"만 만들고, 결정 버튼은 담당자만 누릅니다. (코드에는 점수로 계산한 "AI 예상 합격 참고값"이 담당자 화면에 있는데, 이건 모델이 정한 값이 아니라 프로그램이 75점 이상 합격, 65~74 보류, 그 미만 불합격으로 나눈 것입니다 — recruiter/router.py. 12번 절 "불일치" 참고.)

3. 데이터 창고(DB)와 "한 번만 지원" 규칙

어떻게 같은 사람이 같은 공고에 두 번 지원하지 못하게 하는 규칙을 데이터베이스 자체에 걸었습니다. migrations/versions/20261027_0001_initial.py:210: UNIQUE (posting_id, candidate_id). "한 번에 하나만 진행 중인 발언(turn)", "코딩 최종 제출은 지원 건당 정확히 1개" 같은 규칙도 같은 방식입니다(ux_turn_live, application_id uuid NOT NULL UNIQUE).
왜 화면에서 "이미 지원했어요"라고 막는 것만으로는 부족합니다. 두 번 빠르게 누르거나 일부러 요청을 보내면 뚫립니다. 창고 문에 자물쇠를 달면 누가 어떻게 와도 두 번째는 들어갈 수 없습니다. 이 프로젝트의 철학은 "중요한 규칙은 프런트가 아니라 서버·DB가 지킨다"입니다.

지원 건(application)이 걸어가는 상태

왜"제출 상태", "평가 상태", "합격 결정"을 세 개의 다른 칸으로 나눴습니다. 만약 한 칸에 다 섞으면 "평가가 실패했다 = 응시가 없던 일" 같은 사고가 납니다. 지금은 평가가 실패해도 지원자는 다시 면접을 볼 필요가 없고, 담당자가 다시 평가 버튼만 누르면 됩니다.

5. 면접 진행 — 시계는 서버가 가진다

어떻게 질문 음성이 끝난 뒤에야 서버가 open_answer()를 호출해 상태를 PRESENTING→ANSWERING으로 바꾸고, 그때 서버 시각으로 마감 시각(deadline_at = now + 제한시간)을 정합니다 (interview/turns.py:165~177). 답변은 finalize() 한 곳에서 "정확히 한 번만" 확정됩니다. 버튼과 시간 만료가 동시에 와도 on_conflict_do_nothing과 행 잠금(with_for_update)으로 한쪽만 이깁니다.
왜 브라우저의 시계는 지원자가 마음대로 바꿀 수 있습니다. 그래서 "몇 초 남았나"는 서버만 압니다. 화면의 카운트다운은 보여 주기용입니다. 또 질문 음성이 끝나기 전에는 마이크 입력을 받지 않아서, 질문을 듣는 도중 말한 내용이 답변에 섞이지 않습니다.

중간에 나가면?

어떻게창을 닫거나 새로고침하거나 음성 연결이 끊기거나 신호가 120초 없으면 응시가 INTERRUPTED→EXPIRED로 끝납니다. 이미 답한 문항은 평가하고, 코딩테스트 중이면 마지막 저장 코드를 자동 제출합니다. "이어하기·그만두기·다시 보기"는 일부러 없앴습니다 (ADR-0024, 서버가 409 ATTEMPT_ENDED 등으로 강제).
왜사용자 지시(2026-11-09)가 직접적인 이유입니다. ADR-0024에는 지시 내용만 있고 이유 설명은 없습니다. (제 추측: 이어하기를 허용하면 질문을 보고 준비해서 다시 들어오는 편법이 가능해집니다.) 확실한 사실은, 서버가 강제하므로 화면을 우회해도 이어갈 수 없다는 점입니다.

6. 평가와 점수 — AI는 의견만, 계산은 프로그램이

왜 AI는 같은 질문에도 매번 조금 다르게 말하고, 가끔 계산을 틀립니다. 그래서 AI는 "1~5점 중 몇 점인가"만 말하고, 평균·가중치·총점 계산은 전부 프로그램(evaluation/scoring.py)이 합니다. 가중치 합이 100이 아니면 ValueError("weights must sum to 100")로 저장을 거부합니다.

계산 순서 (코드 그대로)

  1. 질문마다 4개 항목(전문성·논리성·표현 및 태도·전달력)에 AI가 1~5점. 꼬리질문이 있으면 본질문 점수와 평균.
  2. 항목별로 모든 질문의 평균 × 20 → 100점 만점으로 바꿈.
  3. 프로그램이 직접 잰 값(말 속도·발음·부정적 표현 횟수 등)이 있으면 그 항목 점수의 30%로 섞음 (RULE_WEIGHT = 0.3).
  4. 항목 점수 × 가중치(%)를 모두 더해 총점. 코딩테스트가 있으면 코딩 점수 × 코딩 가중치도 더함.
  5. 소수점 둘째 자리에서 반올림(ROUND_HALF_UP)해서 저장.

예시 — 실제 함수를 돌린 결과

평가 기준표(루브릭)는 어떻게 AI에게 전달되나

어떻게ai/rubric.py의 ITEMS에 항목(전문성·논리성·표현 및 태도·전달력)마다 1~5점 기준 문장(levels)과 점수별 예시 답변(examples)이 있습니다. render()가 이를 프롬프트로 만들어 AI에게 줍니다. 질문 유형(경험·행동·기술·설계·상황 대응)마다 "이 질문에서 보는 것" 문단이 따로 붙습니다(QUESTION_KINDS). 예시 답변은 질문 유형이 바뀌어도 그대로이고, 모두 "느려진 API" 한 장면입니다.
주의점수 판단 자체는 AI의 해석입니다. 같은 답변에도 ±1점 흔들릴 수 있고, 그래서 ADR-0023에서 "독립 판정의 중앙값"을 쓰도록 했습니다. 사람 채점과 비교한 정확도 측정은 이번에 찾지 못했습니다. 논리성의 세부 항목(주장 명확성·근거 제시·논리적 흐름)은 한 줄 정의만 있고 점수별 기준·예시가 없습니다(rubric.py:139~144).

7. 근거 인용 검증 — "문장 번호"로 거짓말 막기

리포트에는 "이 점수는 지원자가 이렇게 말해서"라는 근거 문장이 붙습니다. AI는 그럴듯한 문장을 지어내거나, 한두 글자 틀리게 베껴 쓸 수 있습니다.

어떻게sentences()가 마침표·줄바꿈 기준으로 답변을 자르고(160자 넘는 문장은 쉼표에서 더 자름, 최대 40조각), numbered()가 [1] … 목록을 만듭니다. AI는 번호 하나만 돌려주고, 프로그램이 그 번호의 원문 구간(Span: 시작·끝 위치)을 저장합니다.
왜예전에는 AI가 문장을 직접 베껴 쓰게 하고 원문과 대조했습니다(find_span(), 띄어쓰기·따옴표 차이는 봐주되 숫자는 정확히: "3.5배"가 "35배"로 통과하지 않음). 그런데 실제 면접에서 인용을 비워서 내용이 있는 답변이 1점 받는 일이 일어났습니다(ADR-0023 배경). 번호 방식은 "베껴 쓰다 틀리는" 문제 자체를 없앱니다. AI는 존재하지 않는 문장을 만들 수도, 잘못 옮길 수도 없습니다.
주의근거를 찾지 못하면 리포트에 "근거 미연결 / 내용 부족 / 근거 추출 실패 / 답변 없음"으로 구분해서 표시합니다. 예전에는 근거 추출 실패만으로 최저점을 주던 것을 ADR-0023에서 바꿨습니다.

8. 작업 큐 — 번호표를 받은 일은 잊어버리지 않는다

평가·질문 만들기·코드 채점·메일 같은 일은 오래 걸려서 요청 중에 하지 않고 "작업"으로 DB에 적어 둔 뒤 worker가 가져가 처리합니다.

장치어떻게왜
같은 트랜잭션에서 등록enqueue(db, …)는 호출한 쪽의 DB 트랜잭션 안에서 작업 행을 INSERT (queue.py). 예: 답변이 확정(finalize)되는 순간 pre_evaluate 작업도 같이 저장"제출은 됐는데 평가 작업 등록은 안 됨"이라는 반쪽 상태가 생기지 않게 (둘 다 되거나 둘 다 안 되거나)
중복 방지dedupe_key가 같은 살아 있는 작업이 있으면 ON CONFLICT DO NOTHING버튼을 두 번 눌러도 평가가 두 번 돌지 않게
가져가기FOR UPDATE SKIP LOCKED (worker.py:81) — 다른 worker가 잡은 줄은 건너뜀여러 worker가 같은 일을 동시에 집어 가지 않게
임대(lease)가져가면 60초짜리 임대, 15초마다 연장. 연장이 끊기면(worker 사망) 다시 가져갈 수 있음 (worker.reap()이 재시작 때 회수)worker가 죽어도 일이 영원히 "처리 중"으로 남지 않게 → 재시작 후 복구
펜싱 토큰가져갈 때마다 새 번호(lease_token)를 줌. 완료는 "내 토큰이 맞을 때만" 반영 (fenced_complete)늦게 깨어난 옛 worker가 새 worker의 결과를 덮어쓰는 사고 방지
인프라 장애모델 서버가 꺼져 있으면 worker의 "줄"이 일을 아예 가져가지 않고(probe), 횟수도 소모하지 않음 (runtime.py, AC-18)서버가 꺼진 동안 일이 "실패"로 소진되면 억울하기 때문
줄(lane) 분리LLM / LLM_EVAL / RUNNER / CPU / NONE 별로 일꾼 수를 따로 둠 (runtime.py:24)오래 걸리는 평가가 질문 만들기를 막지 않게
왜 별도 큐 제품 대신 DB를 썼나?코드 주석(queue.py)이 밝힌 이유는 "상태 변경과 후속 작업이 함께 커밋되게"입니다. 나머지는 제 해석입니다: 핵심 규칙(원자적 등록, 재시작 복구, 중복 방지)을 가장 간단하고 믿을 수 있게 지키려고 PostgreSQL을 "진실의 원천"으로 썼습니다. Redis는 "일 왔어요" 알림을 빨리 전하는 용도일 뿐이고, Redis가 꺼져도 DB에서 직접 가져가는 길이 있어서 일이 사라지지 않습니다 (runtime.py _next_job, ADR-0013).

9. 코딩테스트 — 유리방(샌드박스)

지원자가 쓴 코드는 믿을 수 없는 코드입니다. 컴퓨터를 망가뜨리거나 정답을 훔쳐볼 수도 있습니다. 그래서 코드를 돌릴 때마다 새 유리방(컨테이너)을 만들고, 끝나면 부숩니다.

잠금 장치 (docker create 옵션)막는 것
--network none인터넷·내부 서버로 연결 (정보 빼돌리기)
--read-only + --tmpfs디스크에 파일 쓰기 (쓸 수 있는 곳은 임시 메모리 영역뿐)
--cap-drop ALL, no-new-privileges관리자 권한 얻기
--user 10001root로 실행
--pids-limit프로세스를 무한 복제(fork 폭탄)
--memory = --memory-swap, --cpus, ulimit (nofile/fsize/core/cpu)메모리·CPU·파일 크기 독점
--ipc none, --log-driver none프로세스 간 몰래 통신, 로그로 정보 유출
왜 "만든 설정이 정말 적용됐는지"를 다시 검사합니다(validate_inspect). 컨테이너만 쓴다고 자동으로 안전한 게 아니기 때문입니다. 비공개 테스트케이스와 정답은 지원자 화면·API·로그·AI 프롬프트 어디에도 나오지 않고, 실행(공개 예제로만)과 최종 제출(공개+비공개 채점)을 구분합니다.
주의 (중요) HANDOFF.md에 따르면 개발 PC(Windows + Docker Desktop, runtime runc)에서 자체 점검 SBX-01~14는 통과했지만 이는 "개발 검증"일 뿐입니다. 운영 Linux에서는 gVisor(runsc)로 다시 통과해야 합니다. 이번에 다시 돌려 확인하지는 않았습니다. 그 전에는 임의 코드 실행을 외부에 열면 안 됩니다.

10. 질문 만들기 — 신입에게 어려운 질문을 하지 않기

어떻게questions/level.py가 이력서의 일한 기간을 더해(인턴·알바·교육은 제외) 수준을 정합니다. 1년 미만 NEW, 1~5년 JUNIOR, 5년 이상 SENIOR (career_level, 65행). 공고가 "신입"만 원하면 SENIOR를 JUNIOR로 낮춥니다. 그다음 difficulty_plan()이 "기초 : 실무 적용 : 심화" 비율로 질문 난이도를 나눕니다 (MIX, 24행).
왜실제 면접 기록에서 신입에게 Kafka·Redis·Prometheus를 함께 엮은 설계 질문이 나갔고, 지원 동기 칸에서 시스템 아키텍처를 묻는 일이 있었습니다(ADR-0025 배경). 그래서 (1) 수준을 코드가 계산하고, (2) 질문이 나오면 코드가 다시 검사합니다 — 기술이 3개 이상 섞였거나, 신입에게 심화 복잡도면 거절 (problems(), fits_level()). AI에게 "신입에게 쉽게 물어봐"라고만 부탁하지 않고 프로그램이 직접 확인하는 것이 핵심입니다.

질문을 언제 만드나? (upfront vs live)

어떻게core/config.py:55의 question_mode 기본값은 "upfront"(면접 시작 전에 10개를 미리 확정)입니다. "live"(질문을 면접 중에 즉석에서 만들기)는 설정으로 남겨 두었습니다.
왜ADR-0025에 따르면 6GB GPU에서 질문 하나를 만들 때 프롬프트 처리만 약 6초, 검증에 실패해 재시도하면 두 배가 걸려서 질문 사이 대기가 10~40초가 되었습니다. 미리 만들어 두면 면접 중 끊김이 없고, PRD 원래 규칙(면접 전에 본질문 확정, 응시 시점의 불변 스냅샷)과도 맞습니다. 이 수치는 문서에 적힌 측정값이며 이번에 다시 재지는 않았습니다.
