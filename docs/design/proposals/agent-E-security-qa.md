# 에이전트 E 설계안 — 보안 및 품질 검증

- 작성: 에이전트 E(보안·품질 검증). 설계 1단계 독립안이며 다른 에이전트(A~D, F)의 설계안은 읽지 않았다.
- 기준 문서: `통합 PRD.pdf` v1.0 초안, `docs/requirements-traceability.md`(우선순위·인수 기준의 기준), `docs/open-questions.md`, `docs/risks.md`, `docs/environment.md`, `docs/prd/integrated-prd.extracted.txt`.
- 상태: **제안**(조정자 F 검토 전). PRD에 없는 수치는 모두 제안값이며 설정값으로 분리한다. PRD에 없는 통제는 "(원문 외)"로 표시한다.
- 성격: 회사가 직접 운영하는 자사 서비스의 방어 설계와 검증 기준이다. 공격 절차는 적지 않고, 방어 통제와 그 통제를 확인하는 테스트만 적는다.
- 이 문서의 ID: 위협 `TH-`, 통제 `SC-`, 샌드박스 자체 점검 `SBX-`, IDOR 매트릭스 행 `M-`, 품질 게이트 `QG-`, 위험 `RE-`, 이 문서가 제기하는 질문 `E-Q`.

## 1. 범위와 전제

### 1.1 범위

1. 위협 모델(자산·행위자·신뢰 경계)과 통제 목록
2. 코딩테스트 샌드박스의 위협 모델, 격리 기술 비교, 설정값, 자체 점검 스위트, "검증 전 비노출" 구현
3. AI 고유 위험(프롬프트 인젝션, 인용 위조, 합불 추천, 평가 입력 개인정보, 편향, 외부 AI API 부재 검증)
4. 인수 기준 AC-01~AC-22 테스트 설계, IDOR 매트릭스
5. 품질 게이트와 정적 분석·의존성 검사 도구, 오프라인 운영 한계
6. 보안 HTTP 헤더, 쿠키 속성, CORS

범위 밖: 법률 검토 대상(동의 문구, 보관 기간 — X-13, OQ-04), 외부망 TURN 구성(OQ-18), 모델 선정(X-11), 부하 용량 확정(OQ-15).

### 1.5 신뢰 경계

```text
[브라우저(지원자/담당자)]
   │ TB-1  HTTPS(쿠키 세션+CSRF)  /  WebRTC(DTLS-SRTP, 시그널링은 HTTPS)
[리버스 프록시] ── [API(FastAPI)] ──TB-2── [PostgreSQL] ──TB-2── [worker]
                      │ TB-3 사설망/루프백: [Ollama][STT][TTS][임베딩]  (출력은 비신뢰 데이터)
                      │ TB-4 루프백 RPC + 내부 토큰
                   [runner] ──TB-5 Docker API── [Docker 데몬] ──TB-6── [샌드박스 컨테이너]
TB-7: 서버 전체 ↔ 외부 인터넷 (운영은 이그레스 차단)      TB-8: 운영자 CLI·DB 관리자 ↔ DB
```

TB-6이 가장 위험한 경계다(임의 코드). TB-5는 권한이 가장 집중된 경계다(Docker 소켓 = 호스트 root 동등). TB-3은 방향이 반대인 경계다: AI 서비스 자체는 사내 것이지만 그 출력은 지원자가 넣은 텍스트의 영향을 받으므로 신뢰하지 않는다.

### 1.6 테스트 계층과 공통 장치

| 계층 | 내용 | 필요 환경 |
|---|---|---|
| 단위 | 순수 함수(점수, 인용 검증, 비식별화, 정책 판정, 프레임 게이트) | 없음 |
| API 통합 | 실제 PostgreSQL(컨테이너) + 가짜 LLM·STT·TTS, httpx 클라이언트 | Docker |
| 샌드박스 통합 | 실제 runner + Docker, SBX 스위트 | Docker(운영 판정은 Linux 서버) |
| WebRTC 통합 | aiortc 테스트 클라이언트가 합성 음성(로컬 TTS 산출 WAV)을 송출 | 로컬 STT |
| E2E | Playwright + Chrome 가짜 장치(`--use-fake-device-for-media-stream`, `--use-fake-ui-for-media-stream`, `--use-file-for-fake-audio-capture`) | 전체 스택 |
| 실모델 통합 | 실제 Ollama 모델로 비결정적 항목을 임계값으로 판정(nightly) | GPU |
| 수동 | 사람의 실제 발화, 청취 품질, 외부망 | 체크리스트 |

공통 장치: **가짜 LLM**(응답 대본 주입 + 받은 프롬프트 캡처), **가짜 시계**(서버 시간 주입점), **카나리아**(테스트마다 고유한 문자열 `CANARY-<용도>-<난수>`를 메모·가중치·인용·비공개 테스트·개인정보 칸에 넣고, 나오면 안 되는 곳에서 검색).

## 2. 설계 대안 비교

### 2.1 코딩테스트 샌드박스 격리 기술

| 기술 | 격리 경계 | 장점 | 단점 | 개발 장비(Win10 + Docker Desktop/WSL2) | 운영(Linux) | 판정 |
|---|---|---|---|---|---|---|
| Docker(runc) + 강화 옵션 | 네임스페이스·cgroup·seccomp·capability, 커널 공유 | 이미 설치됨, 시작 빠름, 옵션만으로 네트워크·자원 제한 | 커널 취약점 하나로 탈출 가능. 단독으로는 신뢰할 수 없는 코드 실행에 부족(R-06) | 가능. 컨테이너는 Docker Desktop의 Linux VM 안에서 돈다. 탈출 도달점은 VM이지만 그 VM은 Windows 드라이브에 접근할 수 있으므로 안전 경계로 보지 않는다 | 가능 | 개발 기준선. 운영 단독 사용 금지 |
| + rootless Docker 또는 userns-remap | 컨테이너 root ≠ 호스트 root | 탈출 시 피해 축소 | 데몬 전체 설정, 일부 볼륨·네트워크 기능 비호환 | Docker Desktop 데몬 설정 변경은 지원·유지가 불확실 → 미검증 | 가능(rootless 권장) | 운영 필수(둘 중 하나) |
| gVisor(runsc) | 사용자 공간 커널이 시스템 호출을 가로챔 | 런타임만 교체(`--runtime=runsc`), 강화 옵션 그대로, 호스트 커널 노출면 크게 축소 | 시스템 호출 성능 저하, 일부 호출 미지원(Python 단일 언어라 영향은 작을 것으로 예상, 실측 필요) | Docker Desktop VM에 runsc를 넣는 것은 공식 경로가 아니고 업데이트 시 사라질 수 있다. 일반 WSL 배포판도 없다 → 비현실적 | **권장** | 운영 1순위 |
| nsjail | 네임스페이스+seccomp-bpf+cgroup+rlimit를 프로세스 단위로 | 가볍고 정책이 세밀함, 채점 서버 사용 사례 | 커널 공유(runc 계열), 설정 난도, Docker 안에서 돌리려면 바깥 컨테이너에 높은 권한 필요 | 중첩 실행은 바깥 권한 상승이 필요 → 비권장 | 가능 | 대안으로 기록만 |
| Firecracker(microVM) | 하드웨어 가상화(KVM) | 가장 강한 경계 | `/dev/kvm`, 커널·rootfs 이미지·jailer 운영 부담 | Windows 10의 WSL2는 중첩 가상화를 지원하지 않는 것으로 안다(확인 필요) → 불가 | KVM 있는 물리 서버만 | MVP 범위 밖 |
| 컨테이너 없는 하위 프로세스 + rlimit | 같은 OS 사용자 | 단순 | 네트워크·파일시스템 격리 없음, Windows에는 rlimit 없음 | — | — | 금지 |

Docker Desktop의 Enhanced Container Isolation은 유료 구독 기능이므로 전제하지 않는다. **결론**: 개발은 "runc + 강화 옵션 + 자체 점검"을 *개발 검증*으로만 인정하고, 운영 출시 판정은 "runsc + rootless(또는 userns-remap) + 같은 강화 옵션"에서 자체 점검을 다시 통과한 결과로만 한다(E-Q9).

### 2.2 runner 배치

| 안 | 내용 | 평가 |
|---|---|---|
| R-a | API 프로세스가 Docker SDK를 직접 호출 | API 취약점 하나가 호스트 장악으로 이어짐 → **기각** |
| R-b | 별도 runner 서비스만 Docker 소켓 접근, API·worker는 좁은 RPC로 요청(4절 계약) | 권한 집중을 작은 코드로 한정 → **권장** |
| R-c | R-b + Docker 소켓 프록시(허용 API 경로만) | 경로 단위 필터라 컨테이너 생성 본문(Privileged 등)은 못 막는다. 주 통제는 runner 내부의 고정 HostConfig + 생성 직후 inspect 검증(SBX-01). 프록시는 보조(원문 외, A 판단) |
| R-d | 미리 띄운 컨테이너 풀에 exec로 재사용 | 지원자 간 상태 잔존, exec API 필요 → **기각**. 실행마다 새 컨테이너, 종료 후 삭제 |

### 2.3 비공개 테스트 주입·채점 방식

| 안 | 방식 | 누출·조작 위험 | 판정 |
|---|---|---|---|
| G-a | 테스트 파일(입력+기대 출력)을 컨테이너에 넣고 안에서 비교 | 제출 코드가 기대 출력을 읽거나, 같은 경계의 채점 하네스를 조작(조기 종료·결과 위조) | 기각 |
| G-b | 테스트 1건 = 컨테이너 1회. 입력은 stdin, 비교는 컨테이너 밖 worker | 컨테이너는 그 테스트의 입력만 본다. 기대 출력은 runner에도 보내지 않는다 | **권장** |
| G-c | 제출 1건 = 컨테이너 1개, 내부 하네스가 입력을 차례로 실행 | 모든 비공개 입력이 한 경계에 모임. 기대 출력은 여전히 밖 | 성능 문제 시 차선 |

G-b는 테스트 수만큼 컨테이너를 띄운다. 채점은 비동기라 지원자 대기와 무관하지만 리포트 목표(8.2: 3분, 최대 10분)와 경합하므로 실측 후 문제당 테스트 수 상한(제안: 20)을 정한다(RE-13). 채점 결과는 지원자에게 돌려주지 않으므로(6.6) 오류 메시지·타이밍을 통한 비공개 테스트 누출 경로는 [실행]에만 남고, [실행]은 공개 예시만 쓰므로 비공개 정보가 개입하지 않는다.

### 2.4 세션 vs JWT

| 기준 | 서버 세션(불투명 토큰, DB 저장) | JWT(서명 토큰) |
|---|---|---|
| 2시간 슬라이딩(USR-06) | 서버가 last_seen 갱신 | 재발급 반복, 구현 복잡 |
| 로그아웃·강제 무효화 | 행 삭제로 즉시 | 차단 목록 필요 → 결국 상태 저장 |
| 역할·회사·계정 비활성 반영 | 즉시 | 만료까지 옛 클레임 유효 |
| 저장 위치 | HttpOnly 쿠키 | 쿠키면 같고, localStorage면 XSS에 노출 |
| 이 환경 적합성 | 단일 서버·소수 사용자에 충분 | 분산 무상태 이점이 무의미 |

판정: **서버 세션**(조정자 잠정안과 같음).

### 2.5 회사 단위 격리: 앱 레벨 vs RLS

| 안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| I-a 앱 레벨: 라우트 정책 선언 + 범위 헬퍼 + 정적 규칙 + IDOR 매트릭스 | 단순, 지원자(소유자 기준)·담당자(회사 기준) 규칙을 한곳에서 표현 | 헬퍼를 우회한 쿼리 한 줄이 누출 → 정적 검사·매트릭스 테스트로 보완 | **필수** |
| I-b PostgreSQL RLS(`SET LOCAL app.company_id`) | 앱 실수에도 DB가 거부 | 커넥션 풀·비동기에서 트랜잭션마다 설정 필요, 테이블 소유자·superuser는 우회(FORCE RLS·별도 롤 필요), worker·CLI 경로 정책 별도 | 심층 방어 선택지(E-Q7) |
| I-c 회사별 스키마·DB 분리 | 강한 분리 | 질문은행·통계·마이그레이션 복잡 | 기각 |

### 2.6 CSRF 방어 조합

| 안 | 평가 |
|---|---|
| SameSite 쿠키만 | 같은 사이트(형제 서브도메인) 요청, Lax의 최상위 GET 허용 → 단독 불충분 |
| Double-submit 쿠키 | 서브도메인 쿠키 주입에 약함 |
| Synchronizer 토큰(세션 행에 저장, `X-CSRF-Token` 헤더) + Origin 검사 + SameSite | **권장**. SPA가 로그인 응답·`GET /api/auth/session`에서 토큰을 받아 상태 변경 요청에 첨부 |

### 2.7 PDF 파싱 격리

| 안 | 평가 |
|---|---|
| P-a API 프로세스 안에서 즉시 파싱 | 파서 무한 루프·메모리 폭주가 API 전체를 멈춤 → 기각 |
| P-b 별도 하위 프로세스(시간·메모리 상한) 또는 worker 작업 | **권장**. 운영 Linux는 rlimit(AS)로 메모리 상한, Windows 개발은 시간 상한만 보장(RE-08) |
| P-c 코드 샌드박스와 같은 컨테이너 격리 | 가장 강함. 운영에서 runner를 재사용할 수 있으면 선택(원문 외) |

파서는 순수 Python 계열(pypdf, pdfminer.six)을 우선한다(메모리 손상 취약점 부류 회피). PyMuPDF는 AGPL이라 라이선스 검토 대상이다. 선택은 B·C 몫이고, 여기서는 위 상한과 픽스처 테스트(AC-06)를 요구한다.

### 3.3 보안 HTTP 헤더·쿠키·CORS

| 헤더 | 운영 값 | 비고 |
|---|---|---|
| Content-Security-Policy | `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; media-src 'self' blob:; font-src 'self'; connect-src 'self'; worker-src 'self' blob:; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` | 외부 출처 없음. 코드 편집기가 동적 style을 주입하면 nonce 또는 `style-src 'unsafe-inline'`을 예외로 기록(D와 합의). 개발 서버(Vite HMR)는 별도 완화 정책, 테스트는 운영 빌드로 |
| Permissions-Policy | `microphone=(self), camera=(self), display-capture=(), geolocation=(), payment=(), usb=()` | 마이크·카메라는 같은 출처만 |
| Strict-Transport-Security | `max-age=31536000` | HTTPS 운영에서만. includeSubDomains·preload는 사내 도메인 정책 확인 후 |
| X-Content-Type-Options | `nosniff` | 모든 응답 |
| Referrer-Policy | `no-referrer` | |
| X-Frame-Options | `DENY` | 구형 호환(frame-ancestors와 중복) |
| Cross-Origin-Opener-Policy | `same-origin` | |
| Cross-Origin-Resource-Policy | `same-origin` | 파일 응답 포함 |
| Cache-Control | API·파일 `no-store` | 개인정보 응답 캐시 금지 |
| Set-Cookie(세션) | `__Host-sid=<토큰>; Path=/; Secure; HttpOnly; SameSite=Strict` | 만료 미지정(브라우저 세션 쿠키), 2시간 판정은 서버. Strict vs Lax는 E-Q6 |

- CORS: 허용하지 않는다. SPA와 API는 같은 출처(리버스 프록시)이며 운영에 CORS 미들웨어를 넣지 않는다. 개발은 Vite 프록시로 같은 출처를 만든다. `allow_origins=["*"]` + 자격 증명은 금지.
- Host 헤더 허용목록(TrustedHost)으로 DNS 리바인딩을 막는다. Origin 검사는 상태 변경 메서드 전부에 적용한다.
- 개발 프로필이 `http://localhost`를 쓰면 `Secure`·`__Host-` 동작이 브라우저마다 다를 수 있으므로 설정 플래그로 분리하고, 운영 프로필에서 꺼져 있으면 기동 실패(SC-61).
- CSP는 RTCPeerConnection의 연결 대상을 제한하지 못한다. 그래서 SC-43(ICE 설정)이 따로 필요하다.

| `--cpus` / `--cpuset-cpus` | `1` / 전용 코어(예: 10,11) | CPU 독점, STT·API와 경합(RE-15) |
| `--ulimit` | `nofile=64:64`, `fsize=8388608`, `core=0`, `cpu=<제한초+1>` | 파일 핸들, 큰 파일, 코어 덤프, CPU 시간. `nproc`는 같은 UID의 모든 프로세스를 합산하므로 쓰지 않고 pids-limit 사용 |
| `--ipc` | `none` | 공유 메모리 |
| `--log-driver` | `none` | 출력 폭주가 Docker 로그 파일로 디스크를 채우는 것 방지. 출력은 runner가 attach 스트림에서 상한까지만 읽음(구현 시 attach 동작 확인) |
| 마운트·장치 | 없음(바인드·볼륨·`docker.sock`·`--device`·`--gpus` 없음) | 호스트 경로·소켓·GPU 노출 |
| 금지 옵션 | `--privileged`, `--pid=host`, `--network=host`, `--userns=host` | 경계 해제 |
| 환경변수 | 허용목록만: `PYTHONDONTWRITEBYTECODE=1`, `PYTHONIOENCODING=utf-8`, `LANG=C.UTF-8` | 비밀 노출 |
| `--hostname` | `sandbox` | 호스트 정보 |
| 이미지 | `python:3.12-slim` 기반, 다이제스트 고정, setuid 비트 제거, pip 제거, 진입점 = 읽기 전용 런처. 운영은 `docker save/load`로 사전 반입 | 공급망, 권한 상승 |
| 정리 | `--rm` + `--label app=sandbox,job=<id>`, runner가 벽시계 초과 시 kill 후 강제 삭제 | 잔존 컨테이너 |
| 운영 런타임 | `--runtime=runsc` + rootless Docker 또는 userns-remap | 커널 공유 위험 |

코드 전달: 바인드 마운트(Windows 경로 노출, 느린 파일 공유)를 쓰지 않고 **stdin 프레이밍**을 쓴다. 런처가 길이 접두 프레임으로 코드를 버퍼링 없이 읽어 `/tmp/main.py`에 쓰고 `python3 -I /tmp/main.py`로 exec하며, 남은 stdin을 프로그램 입력으로 넘긴다. noexec tmpfs라도 Python이 파일을 읽어 실행하므로 동작할 것으로 예상한다(SBX-14로 확인).

#### 3.4.4 "검증 전에는 실행 기능을 노출하지 않는다" 구현

1. 설정 `CODE_EXECUTION_ENABLED`의 기본값은 `false`(단위 테스트로 고정).
2. 유효 상태 = 플래그 true **AND** 최근 SBX 전부 통과 **AND** 지문 일치 **AND** 점검 후 24시간 이내(제안) **AND** 운영 프로필이면 런타임이 승인 목록(runsc)에 있음.
3. 지문 = runner 버전, 샌드박스 이미지 다이제스트, Docker 엔진 버전, 런타임 이름, seccomp 프로필 해시, 제한값 해시. 하나라도 바뀌면 재점검 전까지 비활성.
4. runner는 기동 시·매일·설정 변경 시 SBX를 실행하고 결과를 `sandbox_verifications`(상태, 지문, 결과 JSON, 시각)에 기록한다. 실패하면 작업 수락을 거부한다. 플래그·상태 변경은 감사 로그.
5. 매 실행 전 SBX-01이 실패하면 그 실행을 중단하고 상태를 FAILED로 바꾼다.
6. 비활성일 때(제안, E-Q3): 담당자는 공고에서 코딩테스트를 켤 수 없고(사유 표시), 이미 켠 공고는 면접 시작 전 점검(INT-14와 같은 위치)에서 시작을 막고 안내한다. [실행]·채점 API는 503 `CODE_EXECUTION_UNAVAILABLE`. 이미 제출된 코드는 채점 대기로 두고 회복 후 채점한다(0점 처리 금지).
7. 상태 상세(지문·결과)는 내부·운영자 전용. 지원자 점검 API에는 가능/불가만 준다.
8. 개발 장비 통과는 "개발 검증"으로만 표시한다. 운영 출시 판정은 운영 Linux 서버에서 SBX를 다시 돌린 결과로만 한다.

### 3.5 IDOR 매트릭스 (역할 × 리소스 × 회사)

픽스처: 회사 X·Y, 담당자 X1·X2·Y1, 지원자 A(X사·Y사 공고 **모두** 지원)·B, 공고 X-OPEN·X-DRAFT·Y-OPEN. 경로는 예시이며 B의 API 계약에 맞춰 바뀐다. 표의 값은 기대 상태 코드.

| 행 | 리소스(대표 경로) | 비로그인 | 지원자 A(소유) | 지원자 B | X사 담당자(X1·X2) | Y사 담당자 |
|---|---|---|---|---|---|---|
| M-01 | 공개 공고 상세 X-OPEN `GET /api/postings/{id}` | 401 | 200 | 200 | 403(E-Q10) | 403(E-Q10) |
| M-02 | 임시저장 공고 X-DRAFT(지원자 API) | 401 | 404 | 404 | 403 | 403 |
| M-03 | 지원 생성 `POST /api/candidate/postings/{id}/applications` | 401 | 201, 재시도 409 | 201 | 403 | 403 |
| M-04 | A의 X사 지원 건 `GET /api/candidate/applications/{id}` | 401 | 200 | 404 | 403 | 403 |
| M-05 | 면접 상태·시그널링·답변 제어 `.../applications/{id}/interview/*` | 401 | 200(상태 조건, 아니면 409) | 404 | 403 | 403 |
| M-06 | 코딩 문제·실행·제출 `.../applications/{id}/coding/*` | 401 | 200(CODING일 때만, 아니면 409) | 404 | 403 | 403 |
| M-07 | 지원자 결과 `.../applications/{id}/result` | 401 | 200(공개 스키마) | 404 | 403 | 403 |
| M-08 | 이력서 등록본 `/api/candidate/resume`(경로에 ID 없음) | 401 | 200(본인) | 200(본인 것만) | 403 | 403 |
| M-09 | 공고 관리 `GET/PUT/DELETE /api/recruiter/postings/{id}`(X사) | 401 | 403 | 403 | 200 | 404 |
| M-10 | 평가 설정 `PUT .../postings/{id}/evaluation-settings` | 401 | 403 | 403 | 200(잠금 전, 뒤 409) | 404 |
| M-11 | 지원자 목록 `GET /api/recruiter/applications?posting_id=`(X사 공고) | 401 | 403 | 403 | 200 | 404(필터 없으면 Y사 건만) |
| M-12 | A의 X사 지원 상세·리포트 `GET /api/recruiter/applications/{id}[/report]` | 401 | 403 | 403 | 200 | 404 |
| M-13 | 원본 PDF `.../applications/{id}/resume-file` | 401 | 403 | 403 | 200 | 404 |
| M-14 | 메모 `.../applications/{id}/notes`(ADM-07) | 401 | 403 | 403 | 200(X1·X2 모두) | 404 |
| M-15 | 결정 `POST .../applications/{id}/decision` | 401 | 403 | 403 | 200(평가 완료 후, 전 409) | 404 |
| M-16 | 재평가 `POST .../applications/{id}/re-evaluate` | 401 | 403 | 403 | 200(ON_HOLD일 때) | 404 |
| M-17 | 통계 `GET /api/recruiter/stats` | 401 | 403 | 403 | 200(X사 집계만) | 200(Y사 집계만) |
| M-18 | 내부 API(runner, 샌드박스 상태 상세, 헬스 상세) | 프록시 미노출, 직접 호출 시 내부 토큰 없으면 401 | 동일 | 동일 | 동일 | 동일 |

검사 방법:
- 라우트 인벤토리(SC-10)에서 경로·메서드를 모두 뽑아 행위자 6종(비로그인, A, B, X1, X2, Y1)과 곱한 테스트를 생성한다. 표에 없는 라우트는 정책 메타데이터로 기대값을 계산하고, 정책이 없으면 실패.
- 404 응답은 **진짜 없는 ID에 대한 404와 본문·헤더가 같아야** 한다(존재 비노출).
- 거부된 변경 요청(PUT·POST·DELETE) 뒤에는 DB 상태가 바뀌지 않았는지 확인한다.
- A가 X·Y 모두 지원했으므로 X1이 Y사 지원 건 ID로 요청하면 404, X사 화면 어디에도 A의 Y사 지원 정보(이력서 스냅샷 포함)가 나오지 않아야 한다.
- 목록·통계·검색 응답에 다른 회사 항목이 섞이지 않는지 카나리아 제목으로 검사한다.

### 3.7 품질 게이트

"매 변경"은 원격 CI가 아직 없으므로(OQ-20) 로컬 검사 스크립트 + pre-commit으로 시작하고 F가 정하는 CI로 옮긴다. 추적표의 "검증 완료"는 아래 게이트의 해당 테스트가 실제로 통과한 상태만 뜻한다.
