### 0.1 표기 규칙

- **우선순위**: P0 출시 필수 / P1 출시 포함 목표 / P2 일정 여유 시. v1.0 값 그대로다.
- **상태**: 이 문서를 쓰면서 추적표와 코드로 직접 확인한 결과다. 자동 시험을 이번에 다시 돌린 것은 아니다.
  - `구현`: 코드에서 동작을 확인했다.
  - `일부 구현`: 요구사항 중 일부만 코드에서 확인했다. 빠진 부분은 비고에 적었다.
  - `미구현`: 코드에서 찾지 못했고 추적표도 미착수다.
  - `보류`: 결정으로 만들지 않기로 했거나 기능을 껐다.
  - `미확인`: 코드에서 있는지 없는지 확인하지 못했다. 구현 안 됨으로 읽지 않는다.
- **(변경)** 표시: v1.0과 내용이 달라졌다. 13장에 원래 내용과 근거가 있다.
- **(신규)** 표시: v1.0에 없던 기능이다. 새 ID를 붙였다(기존 ID는 다시 쓰지 않는다).
- 용어: 지원자, 담당자(기업 채용 담당자), 운영자(플랫폼 운영 팀), 본질문, 꼬리질문, 리포트.

## 1. 제품 개요

### 1.1 목적

기업의 1차 채용 과정을 AI로 자동화하고, 같은 기준으로 평가해 담당자의 판단을 돕는다.

한 줄 정의: 담당자가 공고와 평가 조건을 정하면, 지원자는 브라우저에서 이력서 제출부터 AI 음성 면접과 코딩테스트까지 한 흐름으로 마친다. AI는 정해진 평가 기준으로 근거 있는 리포트를 만들고, 담당자가 리포트를 보고 최종 합격·불합격을 정한다. 모든 AI 처리는 사내(온프레미스) 서버에서 한다.

### 1.2 해결할 문제

| 대상 | 문제 | 해결 방향 |
|---|---|---|
| 담당자 | 1차 면접에 일정 조율과 면접관 시간이 많이 든다 | 지원자는 AI 면접을 보고, 담당자는 정리된 리포트로 검토한다 |
| 담당자 | 면접관마다 기준이 달라 비교가 어렵고 근거가 남지 않는다 | 평가 항목은 고정하고 가중치만 조정한다. 점수마다 답변 원문 근거를 붙인다 |
| 담당자 | 일반 질문으로는 실제 경험을 확인하기 어렵다 | 직무·이력서·회사 자료 기반 질문과 답변에 따른 꼬리질문 |
| 기업 | 외부 클라우드 AI에 지원자 음성·이력서를 보내기 어렵다 | 모든 AI 처리를 사내 서버에서 한다 |
| 지원자 | 준비 단계가 흩어져 있고, 응시 후 상태·결과를 알기 어렵다 | 동의 → 이력서 → 점검 → 면접을 한 흐름으로, 마이페이지에서 상태와 결과 확인 |

### 1.3 범위에 관한 결정 (확인 필요)

- `CLAUDE.md` §0은 "단일 관리자, 기업별 계정·멀티테넌시 제외"를 제품 범위로 정했다.
- 그러나 2026-10-30 사용자 결정으로 화면정의서(기업회원 가입, 운영자 화면)를 따르기로 했고, **현재 코드는 회사별 담당자 계정과 운영자 승인 절차를 갖고 있다.**
- 이 문서는 "현재 구현 기준" 원칙에 따라 코드에 있는 대로 적는다. 두 결정 중 어느 쪽을 최종 범위로 할지는 사용자 확인이 필요하다(14장 Q-01).

## 2. 사용자와 권한

| 사용자 | 하는 일 | 볼 수 있는 것 |
|---|---|---|
| 지원자 | 공고 탐색, 지원, 이력서 제출, AI 면접·코딩테스트 응시, 결과 확인 | 본인 데이터와 6.6의 공개 범위 안의 결과 |
| 담당자 | 공고 관리, 면접 질문·가중치·평가 항목 설정, 회사 자료 등록, 리포트 검토, 메모, 최종 결정, 일정·메일·문의 응대 | 자기 회사 공고의 지원자 데이터. 다른 회사 데이터는 화면·API로 볼 수 없다 |
| 운영자 | 기업 인증 승인·반려, 공고 숨김, 기업 정지, 계정 발급, 평가 재처리 | 기업 인증 서류와 메타데이터. 지원자 답변 내용은 보지 않는다 |

- 담당자 계정은 **기업회원 가입**으로 만든다(USR-09). 회사 도메인 메일은 바로 승인되고, 개인 메일은 운영자가 승인할 때까지 공고를 게시할 수 없다. 운영자 도구(명령줄)로 계정을 발급하는 길도 남아 있다.
- 역할과 데이터 소유권은 모든 요청에서 서버가 검사한다. 화면에서 숨기는 것으로 대신하지 않는다.

## 3. 설계 원칙

| # | 원칙 | 지키는 방법 |
|---|---|---|
| P-1 | 기업 채용을 위한 서비스 | 공고에 지원해야만 면접을 본다. 공고와 무관한 연습 면접은 만들지 않는다 |
| P-2 | 직무·이력서 기반 맞춤 질문 | 질문은 질문은행, 이력서, 공고, 회사 자료를 근거로 만든다. 근거에 없는 내용을 지어낸 질문은 버린다 |
| P-3 | 답변에 따른 꼬리질문 | 꼬리질문은 지원자가 실제로 말한 표현이나 이력서 내용에 근거한다. 횟수 상한이 있고, 판단이 멈추면 건너뛰어 면접이 멈추지 않게 한다 |
| P-4 | 평가 기준과 근거로 표준화 | 평가 항목은 고정하고 담당자는 가중치와 기업 추가 항목만 정한다. 점수의 근거는 답변 원문 문장이고, 근거를 지어낼 수 없게 한다. 근거가 없으면 그 사실을 표시한다 |
| P-5 | 점수는 코드가 계산 | AI는 항목 판정(1~5)·근거·코멘트만 만든다. 평균, 가중치 합산, 코딩 채점, 측정값 반영은 서버 코드가 계산한다 |
| P-6 | 지원자와 담당자 정보 분리 | 지원자 API는 6.6의 공개 범위만 돌려준다. 담당자 메모, 비공개 테스트, AI 참고값은 지원자에게 가지 않는다. 모든 담당자 요청에 회사 조건을 서버가 강제한다 |
| P-7 | 개인정보 보호와 자체 AI 처리 | 이력서·음성·답변·코드와 모든 AI 추론은 사내 서버에서만 처리한다. 외부 AI API는 쓰지 않는다. 평가와 무관한 개인정보(이름·성별·나이·사진)는 평가 입력에서 뺀다 |
| P-8 | AI는 보조, 결정은 담당자 | AI(언어 모델)는 합격·불합격을 정하거나 추천하는 문장을 만들지 않는다. 합불은 담당자 저장으로만 바뀌고 변경 이력이 남는다. **(변경)** 담당자 화면에는 총점 구간으로 코드가 계산한 "참고값"이 보인다(ADM-02, 14장 Q-02) |

## 4. 서비스 흐름

| 단계 | 지원자 | 담당자·시스템 | 관련 기능 |
|---|---|---|---|
| 1. 가입·로그인 | 가입 후 로그인 | 담당자는 기업회원 가입 또는 발급 계정으로 로그인 | USR |
| 2. 공고 확인 | 공고 목록·상세 확인 | 공고 작성·게시, 면접·평가 설정, 회사 자료 등록 | JOB, ADM-05, QST-09 |
| 3. 지원·이력서 | 개인정보 동의 후 이력서 제출 | 이력서 텍스트 추출(스캔본은 OCR) | SEC-01·02, RES |
| 4. 환경 점검 | 카메라·마이크·스피커 확인 | AI 서버 상태, 동시 응시 상한 확인 | INT-01·02·13·14 |
| 5. AI 면접 | 본질문(기본 10개)에 음성으로 답하고 실시간 자막을 본다 | 질문 음성, 실시간 음성 인식, 꼬리질문 | INT, QST, 6.1·6.2 |
| 6. 코딩테스트 | 코드 실행과 최종 제출(켠 공고만) | 격리 실행, 자동 채점 | COD, 6.5 |
| 7. AI 평가·리포트 | 완료 화면, 마이페이지에서 상태 확인, 평가가 끝나면 리포트 열람 | 평가, 근거 확인, 점수 계산 | EVL, RPT, 6.3·6.4 |
| 8. 담당자 검토 | 없음 | 리포트·이력서·코딩 결과 검토, 메모, 일정·메일 | ADM-02·03·07·12·13 |
| 9. 최종 결정 | 결정 후 합격 여부와 피드백 확인 | 합격·보류·불합격 저장과 변경 이력 | ADM-04, 6.6 |

도중에 창을 닫거나 연결이 끊기면 응시는 그 자리에서 끝나고, 답한 질문까지만 평가된다(INT-11).

## 6. 면접 구성과 평가 규칙

### 6.1 본질문 구성 (변경)

공고마다 질문 계획(1~10칸)을 둔다. 담당자가 정하지 않으면 아래 기본 10개를 쓴다.

| 순서 | 분야 | 개수 | 출제 근거 |
|---|---|---|---|
| 1 | 인성 | 1 | 고정 문구 "1분 정도로 간단하게 자기소개를 해 주십시오." |
| 2 | 인성 | 1 | 이력서·공고를 바탕으로 코드가 만든 질문 |
| 3 | 지원 동기 | 1 | 회사 자료·공고, 실패 시 공고로 코드가 만든 질문 |
| 4~6 | 직무 기술 | 3 | 회사 자료·공고, 지원자 수준별 난이도. 실패 시 공고로 코드가 만든 질문 |
| 7~9 | 프로젝트 경험 | 3 | 지원 건의 이력서 스냅샷에 적힌 경험·프로젝트 |
| 10 | 협업 | 1 | 이력서·공고를 바탕으로 코드가 만든 질문 |
| 합계 | | 10 | |

- 담당자는 칸 수(1~10), 칸별 분야, 칸별 질문 문구를 정할 수 있다. 문구를 비운 칸은 자동으로 채운다.
- 계획은 첫 응시가 시작되면 지원 건에 고정된다. 출제된 질문은 바뀌지 않는다(QST-06).
- 코딩테스트는 본질문에 들어가지 않고 면접 뒤 별도 단계로 진행한다(COD-01).

### 6.2 꼬리질문 (변경)

| 규칙 | 내용 |
|---|---|
| 횟수 | 본질문 하나에 최대 1개. 면접 전체 상한은 공고 설정(0~4개, 기본 2개) |
| 만드는 조건 | 답변이 모호하거나 근거·사례가 없을 때, 앞뒤 말이 맞지 않을 때, 이력서 내용과 다를 때. 이력서와 달라도 거짓 여부는 판정하지 않고 확인만 한다 |
| 내용 | 지원자가 실제로 말한 표현이나 이력서 문장을 짚어서 묻는다. 새 주제를 꺼내지 않는다. 구체적인 답변에는 한 단계 깊게, 모호한 답변에는 같은 수준 이하로 묻는다 |
| 판단 제한 | AI가 30초 안에 꼬리질문 여부를 정하지 못하면 건너뛰고 다음 본질문으로 간다. 이 제한은 모델이 멈춘 경우를 위한 안전장치다(ADR-0019). 무응답·내용 없는 답변은 AI 판단 없이 건너뛴다 |
| 표시 | 같은 본질문 번호에 "꼬리질문" 표시만 붙인다. 최대 답변 시간 45초 |
| 점수 | 본질문 답변과 꼬리질문 답변의 항목 점수를 평균해 문항 점수 하나로 만든다. 꼬리질문에 답하기 전에 면접이 끝나면 본질문 답변만으로 평가하고 감점하지 않는다 |

### 6.3 평가 항목 (변경)

모든 문항을 같은 4개 항목으로 평가한다. 항목과 점수별 기준 문장은 고정이고, 담당자는 가중치와 기업 추가 항목만 정한다.

| 항목 | 보는 것 |
|---|---|
| 직무 전문성 | 직무 지식·기술 자체가 정확한가, 적용 방법(도구·절차·수치·조건)이 구체적인가, 직무와 맞는가 |
| 논리성 | 사고·판단 과정과 인과가 일관되는가. 질문 유형별로 본다(경험: 상황·판단·행동·결과 / 기술: 개념·이유·일관성 / 설계: 요구사항·대안·트레이드오프) |
| 표현 및 태도 | 질문에 맞게 성실하게 답했는가, 부정적 표현이 많지 않은가, 주어진 답변 시간을 활용했는가 |
| 전달력 | 핵심을 먼저 말하고 순서 있게 정리했는가, 말의 속도·뚜렷함 |

- 척도는 항목마다 1~5점이고 점수별 기준 문장과 참고 사례를 둔다. 참고 사례와 표현이 비슷한지로 점수를 정하지 않고, 같은 내용을 다른 말로 하면 같은 점수다. 짧아도 정확하고 충분하면 5점을 줄 수 있다.
- 지원자 수준(신입·주니어·경력)은 기준을 해석하는 데만 쓰고 점수를 일괄로 올리거나 내리지 않는다. 신입은 학교·팀 프로젝트도 경험으로 본다.
- 항목 안에 세부 항목 점수와 STAR(상황·과제·행동·결과) 구성 비율을 함께 기록해 리포트에 보여 준다.
- 표정·시선·감정·목소리 특성(성별·나이를 짐작할 수 있는 특성)은 평가에 쓰지 않는다. 화면 이탈 기록(INT-16)도 점수에 쓰지 않는다.
- 기업 추가 항목(ADM-05)은 담당자가 정한 상·중·하 기준으로 판정한다.
- 기준 문장과 프롬프트는 TRD(`docs/TRD.md` 5장)에서 정한다.

### 6.4 점수 계산 (변경)

모든 점수는 서버 코드가 계산한다. AI는 항목 판정(1~5)과 근거·코멘트만 만든다.

| 단계 | 계산 |
|---|---|
| 문항 점수 | 문항마다 항목별 1~5점. 꼬리질문이 있으면 본답변과 평균(6.2) |
| 측정값 반영 | 표현 및 태도(답변 시간 활용, 부정적 표현 수)와 전달력(말의 속도, 뚜렷함, 음성 높낮이)은 측정값이 있으면 "AI 점수 × 0.7 + 측정값 점수 × 0.3"으로 섞는다. 측정값이 없으면(텍스트 답변 등) AI 점수만 쓴다 |
| 항목 점수 | 그 항목의 문항 점수 평균 × 20 → 100점 만점. 평균에 넣는 문항 수는 제출이면 출제된 본질문 수, 중도 종료면 답변 기회가 있었던 본질문 수 |
| 코딩테스트 점수 | 6.5 |
| 총점 | Σ(항목 점수 × 가중치 ÷ 100), 기업 추가 항목과 코딩 포함. 소수 둘째 자리 반올림 저장, 화면은 첫째 자리 |
| '내용 부족'(규칙) | 무응답이 아니면서 매우 짧은 답변: 그 문항 전 항목 1점 |
| '내용 부족'(AI) | AI가 1~2점을 주고 근거 문장이 없는 경우: AI 점수 그대로 |
| '근거 미연결' | 3점 이상인데 근거 문장을 못 가리킨 경우: AI 점수 그대로, 화면에 표시 |
| '답변 없음' | 모든 항목 1점. 리포트에 개수를 따로 표시 |

가중치 규칙:
- 가중치는 공고 단위로 정하고 합이 100이어야 저장된다. 코딩테스트를 켠 공고에서만 코딩 항목이 가중치 목록에 나온다.
- 기본값: 코딩을 끈 공고 직무 전문성 35 / 논리성 25 / 표현 및 태도 20 / 전달력 20. 켠 공고 30 / 20 / 15 / 15 / 코딩 20.
- 첫 응시가 시작되면 가중치가 잠긴다(JOB-06). 결과에는 적용한 평가 기준·가중치·점수 계산 버전을 남긴다.

### 6.5 코딩테스트 채점 (변경)

| 지표 | 비중 | 만드는 쪽 |
|---|---:|---|
| 정확성 | 60 | 코드: 최종 제출 코드의 공개·비공개 테스트 통과율 |
| 효율성 | 20 | AI 1~5점 × 20. 통과 0개면 1점, 시간·메모리 초과가 있으면 최대 2점(코드가 강제) |
| 문제 해결 방식 | 10 | AI 1~5점 × 20 |
| 코드 품질 | 10 | AI 1~5점 × 20 |

- 코딩 점수 = 위 네 지표의 가중 합(100점 만점). [실행] 결과는 점수에 들어가지 않는다.
- 시간이 끝나 자동 제출된 코드와 도중 이탈로 제출된 코드도 같은 방식으로 채점한다. 아무것도 쓰지 않았거나 실행되지 않으면 정확성 0점이다.
- AI 판정은 코드에서 글자 그대로 찾은 인용이 있어야 유지되고, 틀리면 1회 다시 만든 뒤 1점이다. 코드 주석은 AI에 보내기 전에 지운다.
- 문제는 레벨(Lv.0~5)별 문제은행에서 공고의 직무·경력·난이도로 레벨을 정해 지원 건마다 고른다. 같은 공고 지원자도 다른 문제를 받을 수 있다(R-24).

### 6.6 결과 공개 범위 (변경)

| 정보 | 지원자 | 담당자 |
|---|---|---|
| 응시·평가 진행 상태 | 바로 | 바로 |
| 리포트: 총점, 등급, 항목별 점수와 가중치, 질문별 평가와 근거 문장, 강점·개선점, 코딩 점수와 코멘트 | 평가 완료 후 | 평가 완료 후 |
| 합격·불합격 결과와 지원자용 피드백 | 담당자 결정(합격·불합격) 저장 후 | 바로 |

## 7. 상태 정의

지원 건 하나는 응시, 평가, 채용 결정 세 가지 상태를 따로 갖는다. 평가가 실패해도 응시 기록은 흔들리지 않는다.

### 7.1 응시 상태

| 상태 | 뜻 | 다음 상태 |
|---|---|---|
| 응시 전 (READY) | 지원이 접수됐고 아직 면접을 시작하지 않았다. 동시 응시 상한에 걸려도 이 상태로 남는다 | 준비 중, 만료됨 |
| 준비 중 (PREPARING) | 안내 확인, 환경 점검, 질문 준비 중 | 면접 중, 응시 전, 만료됨 |
| 면접 중 (INTERVIEWING) | AI 면접 진행 중. 문항마다 답변을 바로 저장한다 | 코딩 중, 제출됨, 중단됨 |
| 코딩 중 (CODING) | 코딩테스트를 켠 공고만. 제한시간은 서버 시간으로 흐른다 | 제출됨, 중단됨 |
| 중단됨 (INTERRUPTED) | **(변경)** 도중 이탈(INT-11)을 처리하는 순간에만 거치는 상태. 같은 처리 안에서 만료됨으로 넘어간다 | 만료됨, 제출됨 |
| 제출됨 (SUBMITTED) | 모든 단계가 끝났다. 이 순간 평가 작업이 등록된다 | (끝) |
| 만료됨 (EXPIRED) | 도중에 나갔거나, 응시를 끝내지 못한 채 공고가 마감됐다. 답한 문항이 1개 이상이면 그 문항까지만 평가하고 "질문 N/M"을 표시한다. 0개면 평가하지 않는다 | (끝) |

- 응시는 지원 건당 1회다(INT-12). 제출됨·만료됨에서 다시 응시하는 길은 없다.
- 면접·코딩 도중 공고가 마감되면 진행 중인 응시는 끝까지 진행하고 새 시작만 막는다(OQ-27).
- 화면 이탈 경고(INT-16)는 응시 상태를 바꾸지 않는다.

### 7.2 평가 상태

| 상태 | 뜻 | 다음 상태 |
|---|---|---|
| (없음) | 제출 전. 평가 없음 | 평가 대기 |
| 평가 대기 (PENDING) | 제출·만료와 같은 트랜잭션으로 평가 작업을 기록했다. 서버가 재시작돼도 사라지지 않는다 | 평가 중 |
| 평가 중 (RUNNING) | 답변 평가와 종합 리포트를 만드는 중 | 평가 완료, 평가 보류, 평가 대기(작업 반환) |
| 평가 완료 (DONE) | 담당자 리포트와 지원자 결과가 모두 만들어졌다 | (끝) |
| 평가 보류 (ON_HOLD) | 자동 재시도 뒤에도 실패했다. 임시 점수는 만들지 않는다. 지원자에게는 '진행 중'으로 보인다 | 평가 대기(담당자 재평가) |

평가 실패를 끝 상태로 두지 않는다. 모든 제출 건은 결국 평가 완료에 도달해야 하고, 지원자에게 재응시를 요구하지 않는다.

### 7.3 채용 결정 상태 (변경)

| 상태 | 뜻 |
|---|---|
| 검토 전 (UNDECIDED) | 담당자가 아직 결정하지 않았다. 평가 완료 전에는 바꿀 수 없다 |
| 합격 (PASS) | 담당자가 저장했다. 지원자에게 공개된다 |
| 보류 (HOLD) | 담당자가 저장한 내부 상태. 지원자에게는 '검토 중'으로 보이고 공개·메일이 나가지 않는다 |
| 불합격 (FAIL) | 담당자가 저장했다. 지원자에게 공개된다 |

- 합격·보류·불합격은 서로 바꿀 수 있고, 바꿀 때마다 누가·언제·무엇에서 무엇으로 바꿨는지 남긴다. '검토 전'으로는 되돌리지 않는다(OQ-28).
- AI는 이 상태를 바꾸지 않는다(P-8).

### 7.4 공고 상태

임시저장 → 진행 중(게시) → 마감. 마감은 담당자가 하거나 마감일이 지나면 자동으로 된다. 마감된 공고에는 새로 지원할 수 없고, 아직 시작하지 않은 응시는 만료된다. 담당자는 공고를 삭제할 수 있고, 삭제해도 응시자 결과는 남는다(JOB-04). 운영자가 숨긴 공고는 지원자 목록에 나오지 않는다(OPS-02).

## 8. 비기능 요구사항

### 8.1 온프레미스 AI와 기준 장비

- 모든 AI 추론은 사내 서버에서 하고 외부 AI API는 쓰지 않는다(SEC-06).
- 개발·시연 기준 장비는 VRAM 6GB GPU와 RAM 64GB다(X-03). 가장 낮은 장비에서 돌아야 다른 장비에서도 돈다.
- 언어 모델은 6GB에 들어가는 양자화 모델을 질문 생성·꼬리질문·평가에 함께 쓴다. 음성 인식·음성 합성·임베딩 모델은 TRD에서 실측 후 임시로 정했다(ADR-0003, ADR-0004). 팀 최종 확인은 남아 있다(X-11).
- 음성은 브라우저와 서버가 WebRTC로 직접 주고받는다. 시연은 같은 네트워크 기준이고, 외부망 중계 서버(TURN)는 구성안만 있고 미검증이다.

### 8.2 성능 목표

| 항목 | 목표 | 현재(실측, 6GB 장비) |
|---|---|---|
| 본질문 음성 재생 시작 | 1초 안. 본질문 음성은 미리 만든다 | 미리 만든 경우 충족 예상. 면접 중 생성 방식(QST-02 기본값)에서 미리 만들지 못한 질문은 즉석 합성 |
| 실시간 자막 | 말이 끊긴 뒤 2초 안 | 미확인(실제 마이크 측정 없음) |
| 답변 종료 → 다음 질문 | 5초 안 | **미달**. 꼬리질문 판단이 보통 5~7초, 재요청 시 10~14초(ADR-0019). 시작 전 전부 만들기 방식 측정에서 다음 본질문 p50 0.16초·p95 6.8초(ADR-0025). 면접 중 생성 방식의 실제 전환 시간은 미측정 |
| 리포트 생성 | 제출 후 3분 안, 몰려도 10분 안 | 미측정. 답변 1개 평가(3회 판정) 약 33초 측정(ADR-0026) |
| 평가 재시도 | 10분 안에 끝나지 않으면 자동으로 1회 다시 | 구현 |

목표 값은 v1.0 그대로 두고, 맞추지 못한 항목은 실측과 함께 적었다. 목표를 바꿀지는 14장 Q-05에서 정한다.

### 8.3 동시 응시와 안정성

- 동시 응시 상한(기본 2명)을 둔다(INT-13). 부하 측정 후 확정한다.
- 분석 누락 0건: 제출과 평가 작업 등록을 한 트랜잭션으로 묶고, 서버가 다시 켜지면 남은 작업을 다시 집는다. 같은 작업이 두 번 실행돼도 결과는 한 번만 반영된다.
- 답변은 문항마다 바로 저장해, 도중에 끝나도 확정된 답변은 잃지 않는다.
- AI 서버가 응답하지 않아도 면접은 멈추지 않는다. 질문 생성 실패는 공고·이력서로 코드가 만든 질문으로, 음성 합성 실패는 텍스트로, 음성 인식 실패는 '답변 없음'으로 대신한다.
- **(변경)** 연결이 끊기면 응시는 끝난다(INT-11). 지원자 탓이 아닌 장애로도 응시 기회를 잃을 수 있다(R-29).

### 8.4 보안

- 전송 구간은 HTTPS로 암호화한다. 브라우저는 HTTPS나 localhost에서만 마이크를 허용한다.
- 비밀번호는 복원할 수 없는 해시로 저장한다.
- 역할과 회사 조건을 모든 API에서 서버가 강제한다.
- 업로드는 형식·크기를 서버에서 다시 검사하고, 제출 코드는 네트워크가 막힌 격리 환경에서만 실행한다.
- 감사 로그는 남기되, 앱 로그에는 답변 원문과 개인정보를 남기지 않는다.

### 8.5 개인정보와 보관 기간

| 데이터 | 보관 |
|---|---|
| 답변 음성 원본 | 30일 뒤 자동 삭제(잠정) |
| 카메라 영상 | 저장하지 않는다 |
| 답변 텍스트, 리포트, 제출 코드, 이력서 | 365일(잠정) |
| 생년월일, 성별 | **(변경)** 계정 정보로 받는다. 평가·질문 생성 등 AI 입력에는 넣지 않는다 |
| 사진 | 받지 않는다 |

- 보관 기간의 기산점은 결정 저장일(없으면 공고 마감일)이다(OQ-11 잠정).
- 회원이 탈퇴하면 보관 기간과 관계없이 본인 데이터를 지운다(USR-07).
- 보관 기간과 동의 문구는 출시 전에 법률 검토를 받는다(X-13). 채용절차법의 채용서류 보관 상한과 365일이 부딪칠 수 있다(OQ-39).

### 8.6 공정성과 설명 가능성

- 평가 입력에서 이름·성별·나이·사진을 뺀다(EVL-07).
- 시선·표정·감정·목소리 특성으로 평가하지 않는다. 카메라는 본인 화면 표시와 화면 이탈 경고에만 쓴다.
- 모든 점수의 근거는 답변 원문 문장이며, 근거가 없으면 그 사실을 표시한다(EVL-02).
- 평가 품질은 사람이 채점한 골든셋과 비교해 확인한다. 일치도 목표는 Cohen's Kappa 0.6 이상이고, 모델·프롬프트·평가 기준을 바꿀 때마다 다시 돌린다(P1). **골든셋 데이터는 아직 없다(OQ-13).** 지금은 작성자가 만든 합성 답변으로만 순서·일관성을 쟀다(ADR-0023, ADR-0026).
- 같은 공고 지원자도 질문(면접 중 생성, 지원자 수준별 난이도)과 코딩 문제가 다를 수 있다. 평가 항목과 기준은 같다.

### 8.7 지원 환경

- PC의 크롬·엣지 최신 버전. 모바일 응시는 지원하지 않는다.
- 마이크와 카메라가 있어야 응시할 수 있다.
