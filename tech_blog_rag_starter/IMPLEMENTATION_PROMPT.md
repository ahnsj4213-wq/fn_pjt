# 개발 에이전트용 실행 프롬프트

기존 로컬 AI 면접 프로젝트에 기업별 기술 블로그 RAG 데이터를 연동한다. 먼저 저장소의 현재 구조, 문서, DB 스키마, 수집/임베딩 파이프라인을 분석하고 중복 구현을 피한다. 이 패키지의 README.md와 config/companies.yaml을 참고한다.

## 고정 범위
- 대상 기업: 우아한형제들, 컬리, 토스. 각 공식 기술 블로그 20건, 총 60건을 1차 목표로 한다.
- `awesome-korean-tech-blogs`는 회사별 공식 기술 블로그 주소를 확인하는 디렉터리다. 그 저장소에 블로그 본문이 저장돼 있다고 가정하지 않는다.
- 기존 시스템은 Docker Compose 기반 로컬 실행이며 외부 도메인/DNS 또는 공개 서버를 추가하지 않는다.
- 기존 PostgreSQL + pgvector, 로컬 임베딩/LLM을 우선 재사용한다.
- 기존 채용공고·기업·문서 테이블과 관계를 먼저 확인하고 기존 구조를 최대한 활용한다.

## 작업 단계
1. 수집 대상 블로그별 robots.txt, 이용약관, 수집 허용 여부를 확인하고 차단 시 우회하지 않는다.
2. 사이트맵/피드/목록 페이지를 탐색하여 URL 후보를 수집한다. 기술 구현·프로젝트 사례 중심으로 선별하고 인사·행사·광고 글은 제외한다.
3. 기업당 20건까지 HTML 본문을 추출한다. 부족하면 실제 건수와 사유를 기록하며 억지로 채우지 않는다.
4. 원문 URL, 제목, 날짜, 회사 ID, 수집 시각, 콘텐츠 해시, 출처 유형, `is_synthetic=false`를 보존한다. 수집한 문서와 실제 기업 주장 여부를 섞거나 지어내지 않는다.
5. 회사별 문서 3건을 사람이 읽어 본문 품질을 확인한 뒤 전체를 적재한다. 빈 페이지, 메뉴/네비게이션만 포함된 문서, 중복 본문을 제외한다.
6. 기존 데이터 모델에 매핑한다. 벡터 검색 때 회사 ID를 우선 필터링하고 필요하면 공고에 매핑한다. 지원자 이력서와 별도 출처로 관리한다.
7. 청크 기준 500~1000 토큰, overlap 100~150을 출발점으로 시험하고 임베딩 모델에 따라 조정한다.
8. RAG 평가는 기업별 최소 10개 질문으로 시작한다. Hit@5, 근거 문서 URL 정확도, 타사 문서 유입 여부, 근거 없는 질문 비율을 측정한다.
9. 수집 상태/재시도/오류 이유/누적 건수/중복률을 보고하고 새 수집을 재실행해도 중복 적재되지 않도록 만든다.
10. 실행 명령과 실패·차단·목표 미달 대응 SOP를 문서화한다.

## 완료 기준
- 실제 수집 성공 건수가 기업별로 보고되어야 한다. 60건이 확보되지 않았으면 완료라고 선언하지 않는다.
- 각 기업에서 검색한 결과에 다른 기업 문서가 포함되면 실패다.
- 생성된 질문마다 관련 원문 출처 링크와 근거 청크 ID를 제시할 수 있어야 한다.
- 공개 블로그에 없는 내부 시스템 세부 구조는 사실처럼 단정하지 않는다.
- 스키마 변경이나 새 라이브러리를 추가한 경우 이유와 마이그레이션 방법을 기록한다.
